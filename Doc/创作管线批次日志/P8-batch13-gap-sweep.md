## 二、类型码：五个全实证了

做法就是 `TableProvisioner` 里那套探测表的手法，只是这次把五种类型各建一列：

```
探测表已建：tblRR2QIMJfrGAiI（code=0）
读回：文本列 → type=1
读回：数字列 → type=2      ← 这一个以前没验过
读回：单选列 → type=3
读回：多选列 → type=4      ← 这一个以前没验过
读回：复选框列 → type=7
探测表已删：tblRR2QIMJfrGAiI（code=0）
```

以前验不了不是因为懒，是因为**需求表的 schema 里刚好一个数字列、一个多选列都没有**——
真表里不存在的类型，靠真表验不出来。**造一张只为验证而生、验完就删的表**，
是这类「真实但用不上的路径」唯一的验证办法。

## 三、`1069603` 的根因：应用只有「可编辑」，订阅要「可管理」

P8 批次 9 卡在这里，当时只知道「不是 scope 的问题」。这次查到底了。

**证据一**（真调 `GET /drive/v1/permissions/{token}/members?type=bitable`）：

```json
{"member_id":"ou_f876…","member_type":"openid","perm":"full_access"}   ← 用户
{"member_id":"cli_aa0d…","member_type":"appid","perm":"edit"}          ← 我们的应用
```

**证据二**（官方文档原话）：订阅云文档事件这个接口
**「文档的通知事件仅支持文档拥有者和文档管理者订阅」**，
`1069603` 的含义就是**调用身份无文档管理权限**。

两条对上了：应用是 `edit`，差一级。

### 要用户点的（一步）

打开那张多维表格 → 右上角「分享 / 协作者」→ 找到那个自建应用 →
**把权限从「可编辑」改成「可管理」**（有的版本叫「完全访问」）→ 保存。

改完跟 Claude 说一声，它重跑一次订阅接口就能补验；**代码一个字都不用改**。

## 四、一个按钮点出来的四件事——最重的一件是「静默忽略参数」

另一个会话重做面板时真点了一次「试跑」按钮，点出四件事。三件在命令层，本批修掉。

### ① 命令框架**静默忽略认不出来的参数名**（最重）

`Bridges/feishu/driver.json` 的试跑写的是 `bridge.provision --driver feishu --dry-run`，
而属性名是 `Driver` / `DryRun`。**键对不上就被 `JsonSerializer` 默默丢掉**，
命令按默认值跑完、退出码 0、一句提示都没有。
`bridge.provision` 的 `DryRun` 默认是 `false`，所以那一次点「试跑」
**执行了一次真的供给**（供给幂等，没造成损失，产物哈希一字未变）。

同一个坑长在花钱的路上就是烧钱：`bridge.model` 的 Summary 自己写着
「`--dry-run false` 才真发（花积分）」——照那句话写，参数被忽略、走默认值。
这次默认值站在安全那一侧（默认干跑），**但那是运气，不是设计**。

**修法**：`CommandArgumentValidator` 现在把认不出来的参数键当**错误**报，
文案里列出这条命令认的全部参数名。MCP 那条入口也补上了同一道校验
（原来只有命令宿主校验，两条入口行为不一致）。

### ② 两个 driver 的试跑命令参数名写错、一个根本跑不了

| driver | 原来的试跑 | 现在 |
|---|---|---|
| blender / comfyui | `art.caps --driver blender` | `bridge.probe --Driver blender` |
| feishu | `bridge.provision --driver feishu --dry-run` | `bridge.provision --Driver feishu --DryRun true` |
| oaicompat | `task.prereview --DryRun true`（缺必填参数，退出码 2） | `bridge.complete --Driver oaicompat` |

`art.caps` 的参数名其实是 `DriverName`，写成 `--driver` 与 `--DriverName` 都不对；
而且 `art.` 这一族**不在面板的命令白名单里**，按钮按下去也跑不了。
改成 `bridge.probe` 之后：参数名对了、在白名单里、而且它**真的会去起一次 driver 子进程**，
比一条跑不了的命令有用。

### ③ 执行后端终于有了自己的试跑：`bridge.complete`

决策 91 说「能不能用只有真跑一次才算数」，而执行后端一直没有一条能真跑的试跑命令。
新增 `bridge.complete`：发一句最短的提示（缺省「回一个字：通」），看下游通不通。
一次调用几个 token，但它能一次分清「密钥错 / 地址错 / 模型名错 / 余额不够」四种毛病。

真跑输出：

```
服务端报的模型：deepseek-v4-flash
回答字数：1
回答：通
执行后端通了：driver=oaicompat
```

### ④ 留给用户的两个白名单决定

面板的 `POST /cmd` 白名单（决策 19）现在放行 `task.` / `pool.` / `bridge.` /
`engine.` / `conflict.` / `spec.` 六族。两件事要用户点头：

1. **能力对账 `art.caps` 不在白名单里**，所以本地形态 driver 的对账在面板上点不了。
   要不要放 `art.` 进去？（这一批没动它，只把试跑改成白名单内的等价命令。）
2. **`spec.` 这一族至今一条命令都没有**，白名单却放行着它——
   一个空的放行族不会造成危害，但它是「放行范围与真实命令对不上」的信号。
   要不要收窄？（另一个会话真跑面板命令台时发现的：`spec.list` 报「未找到命令」。）

两件都是安全边界的决定，**扩与收都该由用户定**，不由任何一个会话顺手改。
