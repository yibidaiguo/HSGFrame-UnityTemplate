# BUG 反馈簿

> **实际项目里踩到的问题写这里。** 一条 BUG 一节，编号 `BUG-0001` 顺排，只增不改号。
> 修完不删——留着是账，也是「这类问题该不该立成门禁」的证据（攒够同类就进[待办账本](Backlog.md)）。

## 怎么写一条

复制下面这段贴到「## 未处理」下面，编号取当前最大号 +1。**六项写全**，
写不全的项写「不知道」——比空着强，空着会让人以为你确认过没有。

```markdown
### BUG-00XX 一句话现象（动词开头，别写「有问题」）

- **状态**：新报
- **现象**：看到了什么。截图/日志贴路径，别贴大段原文。
- **复现步骤**：1. … 2. … 3. …（能重复出现的写步骤；偶发的写「偶发，N 次里 M 次」）
- **期望 / 实际**：本该怎样 / 实际怎样。两句话，别合成一句。
- **环境**：哪台机器、哪个项目、走的哪条路（面板 / 飞书 / 命令行 / 执行端派活）。
- **影响面**：挡不挡活。挡了写「挡」，能绕写清怎么绕的。
```

**不用你判断根因**，也不用你想修法——那是接手时的事。你只要把「看到了什么」写准。

## 状态怎么流转

| 状态 | 意思 | 谁改 |
|---|---|---|
| 新报 | 刚写下，还没人看 | 你 |
| 确认中 | 有人在复现 | 接手的人 |
| 修复中 | 复现了，正在改 | 接手的人 |
| 已修 | 改完且门禁绿；补上「修在哪个提交」 | 接手的人 |
| 不修 | 有理由不修（设计如此 / 成本不值 / 上游问题）；**理由必须写** | 接手的人 |

已修与不修的条目移到文末「## 已归档」，别删。

### BUG-0003 本机代理把国内域名的直连解析弄坏了，飞书与 DeepSeek 一个都连不上

- **状态**：新报（**上游问题：本机代理配置，不是仓库代码**）
- **现象**：所有走 `open.feishu.cn`、`api.deepseek.com`、`www.baidu.com` 的请求
  在 TLS 握手阶段挂掉（`Received an unexpected EOF or 0 bytes from the transport stream`）。
  `bridge.ensure` 报的是「连不上飞书：无法建立连接（取 token 阶段）」。
- **复现步骤**：1. `curl https://open.feishu.cn/` → 000；
  2. `curl --resolve open.feishu.cn:443:163.177.118.61 https://open.feishu.cn/...` → **400（通了）**；
  3. `curl https://openapi.tripo3d.ai/v3` → **401（通了）**。
- **期望 / 实际**：期望国内域名与国外域名都能连。实际是**只有走代理节点的域名通，判 DIRECT 的国内域名全断**。
- **环境**：Windows；Clash Verge（verge-mihomo）TUN 模式、gvisor 栈、`enhanced-mode: fake-ip`、
  `dns-hijack: any:53`。规则 `RULE-SET,cn_domain,DIRECT,no-resolve`。
- **影响面**：**挡**。挡住飞书全链（供给、推文档、任务表、助手回话）与执行后端（DeepSeek）。
  Tripo 与 GitHub 这类走代理节点的不受影响。
- **根因（已定位到这一步）**：系统 DNS 被劫持成 fake-ip（`open.feishu.cn` → `198.18.0.64`）。
  mihomo 把 fake-ip 映射回域名后命中 `cn_domain,DIRECT,no-resolve`，**直连前要自己再解析一次域名，
  而这一次解析失败**——所以拿真实 IP 绕过 DNS（`--resolve`）就立刻通。
  「TCP 连得上」在 TUN 下不是证据：gvisor 一律先接受 SYN，再去拨上游。
- **不在这里修的理由**：这是本机代理的配置，改它属于动系统网络设置，不该由仓库代码或 AI 代劳。
  绕法：把代理的 TUN 关掉，或给 mihomo 配一个能用的 `direct-nameserver`。

### BUG-0004 Tripo 模型生成一直失败：配置里那把密钥是无效的，而有效的那把余额是 0

- **状态**：新报
- **现象**：`bridge.model` 走 API 一直不出模型（老账记成「API 返回 0」）。
- **复现步骤**：1. 用 `local.json` 里的 `模型生成密钥` 调 `GET /v3/account/balance`
  → `{"code":2,"status":"error","message":"Invalid API key"}`；
  2. 用 Tripo CLI 登录的那把（`~/.tripo/config.json`）调同一个接口
  → `{"code":0,"data":{"balance":0.00,"frozen":0.00}}`。
- **期望 / 实际**：期望配置里的密钥能认证并有额度。实际是**两件事各错一半**——
  配置里那把认证就过不去，能认证的那把额度是 0。
- **环境**：Windows；`Tools/CreationPipeline/Config/local.json` 的 `模型生成密钥`；
  Tripo CLI 装在 `D:\Tools\Tripo	ripo.cmd`（不在 PATH 里）。
- **影响面**：**挡**模型生成的真跑。链路本身可以接通并验证到「下游明确回额度不足」这一步为止。
- **根因与下一步**：不是代理问题（Tripo 域名连得通，401/4001 都是正常回包）。
  密钥这一半已就地改掉（换成 CLI 那把有效密钥）；**额度这一半要人去充值**——
  充值是花钱动作，AI 不做。

### BUG-0002 探活只看端口不看仓库，把人送进别的项目的面板

- **状态**：已修（修在 `Tools/Dashboard/DashboardServer.cs` + `Tools/panel-open.ps1`，2026-08-22）
- **现象**：一台机器上并行开两个项目时，`panel.bat` 说「面板已经在跑，直接开浏览器」，
  打开却是**另一个仓库**的面板——页面一切正常，数据全是别人的。
  实测那一刻：8766 上跑的是 `D:\Projects\Unity\RPG` 的面板，而人是在 GameTemplate 里点的。
- **复现步骤**：1. 在 A 仓库起面板（默认端口 8766）2. 到 B 仓库双击 `panel.bat`
  3. 它探到 8766 有应答 → 判成「B 的面板已经在跑」→ 开浏览器，进的是 A 的面板。
- **期望 / 实际**：期望是问一句「你是谁的面板」，对不上就说清楚并停下。
  实际是只探端口应答，谁应答都算「自己的」。
- **环境**：Windows，多项目并行；`Tools/panel-open.ps1` 的 `Test-面板在跑`。
- **影响面**：不挡活，但**会误导**——最坏的一种：看着别人的数据做决定。
- **根因与修法**：端口应答只能证明「有人在听」，证明不了「听的是我这个仓库的面板」。
  面板新增 `/api/panel/identity`（报仓库根、仓库名、端口），探活时比对仓库根：
  是自己的才叫「已经在跑」；是别的仓库的，把两边的仓库根都摆出来并给两条路
  （去那边停掉 / 这里换端口）；**认不出自己是谁的**（旧版面板没有这个接口）也一律拒绝，
  不许猜。起完之后再核一次身份——等端口的那几秒里端口可能被别人抢走。
- **为什么身份接口不跟着别的接口回 503**：没配仓库根的面板与别的仓库的面板是两回事，
  都不该被当成自己的；回 503 会让调用方以为接口坏了，反而走上「当成自己的」那条路。
  两条都由 `CreationPanelPackagesTests` 守着。

### BUG-0001 影子拷贝撞上被占用的 DLL 时无声死等

- **状态**：已修（修在 `Tools/progress.ps1` + `Tools/start.ps1` + `Tools/dispatch.ps1`，2026-08-22）
- **现象**：起服务的脚本停在「影子拷贝」这一步不动，四分钟零写入、不报错也不退出。
  实测那一刻：robocopy 正往 `HSGFrameRun/<项目>/commandhost` 镜像，而上一轮起的
  飞书助手 `assist.serve` 正从那个目录里跑，锁着 `Toolkit.CommandHost.dll` 等一串 DLL。
- **复现步骤**：1. 起一轮服务（助手会常驻，从影子目录跑）2. 改一次代码重编
  3. 再跑一次 `Tools/start.ps1`，第二次影子拷贝就撞上助手占着的那些 DLL。
- **期望 / 实际**：期望是当场失败并说清「哪个文件被谁占着、先跑 stop.ps1」。
  实际是一声不吭地杵着——robocopy 不带 `/R` `/W` 时默认 `/R:1000000 /W:30`，
  锁住的文件重试一百万次、每次等三十秒，看上去与卡死没有区别。
- **环境**：Windows，`Tools/start.ps1` 与 `Tools/dispatch.ps1` 两处 robocopy 调用都有这个缺陷。
- **影响面**：挡。绕法是先 `Tools/stop.ps1` 停干净再起。
- **根因与修法**（三层，都实测过）：
  1. `Copy-影子` 统一带 `/R:2 /W:1`：撞上锁几秒内失败，并把 robocopy 的错误尾巴摆出来（实测 4 秒）。
  2. **拷之前先查**目标目录里有没有活着的进程，有就直接点名 PID 与命令行、不做无谓尝试（实测 1 秒）。
  3. **起谁才镜像谁**：`start.ps1` 从前无条件镜像 dashboard 与 commandhost 两份，
     于是「只重起面板」也会去动助手正用着的 commandhost。改成按 `-NoDashboard` /
     `-NoAssistant` 决定镜像哪份——助手开着也能重起面板（实测 4 秒起来）。
- **留下的账**：影子目录本身会被上一轮的常驻进程占着，这一点脚本顶上的注释原本没想到。
  真要做到「谁都不用停就能换新产物」，得给每一轮起一个带版本号的运行目录，见
  [待办账本](Backlog.md)。现在这版是「快速失败 + 说清是谁」，不是「不用停」。
