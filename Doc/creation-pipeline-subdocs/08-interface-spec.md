# 界面规格(创作管线子文档 08)

> 状态:草案 · 2026-08-23
> 上游:总方案 §二(需求模型)、§八(美术四域);下游:子文档 06(美术管线)、07(规范与门禁)。
> 本文定**界面规格**这一层的格式与生成关系,不重复讲理念。

## 一、为什么要有这一层

需求说「要做什么」,设计池说「定成什么样」,资产请求说「出一张什么图」。
中间**没有任何东西说「这一屏该有哪些元素、每个元素干什么」**——
资产请求里最接近的是一行自由文本「描述」。

这个缺口的代价是实测出来的:拆图只能反过来干——先出一张美术图,再**从图上猜有哪些元素**。
一屏猜出 100 多个、跟需求对不上、通用件认不出来,三样都是这么来的,
不是切图算法的问题。程序侧同样受害:它拿到的界面结构不是策划定的,
是生图模型随手画出来的。

界面规格就是这一层。它是**功能契约**,不是美术稿:
先定契约再定外观——美术返工不影响程序,程序也不必等美术。

**依赖方向必须是这个,不许反过来:**

```
需求 ──► 界面规格 ──┬──► 布局图(白块,确定性渲染)   ← 给人看、给美术当底稿
                    ├──► uidef ──► UXML/USS/C#      ← 给程序
                    └──► 资产清单 ──► 资产请求 ──► 出图 / 拆图按清单切
```

从前是 `拆图结果 ──► uidef`。那条箭头反了,得掉过来。

## 二、落点与 id

```
Pools/Designs/Interfaces/UI-0007.json        ← 正本(手改与生成都改它)
_Generated/Interfaces/UI-0007.layout.svg     ← 布局图,生成物,幂等门禁查
UI/Definitions/<面板>.uidef.json             ← 生成物(既有落点不变)
```

- 住**设计池**而不是需求目录:一个界面会被多个需求改(背包初版一个需求,
  后来加排序又一个),挂在单个需求下会说不清归谁。它是「定成什么样」,天然属设计池。
- id:`UI-` + 四位递增,与 `REQ-` / `DR-` / `WI-` / `ASSET-` 同族规则(子文档 01 §一)。
- 目录名 ASCII(`Interfaces/`),字段名中文——与全仓一致(决策 1)。

## 三、面板级字段

| 字段 | 类型 | 说明 | 所有权 |
|---|---|---|---|
| id | string | UI-xxxx | 工程 |
| 面板 | string | PascalCase,决定 uidef 名与资产模块目录(`Art/Texture/Ui/<面板>/`) | 工程 |
| 标题 | string | 人话名字 | 策划端 |
| 来源需求 | array | REQ-id;**可多条**,这一屏被哪些需求改过 | 工程 |
| 关联定稿 | string | 风格定稿@vN,缺省取所属专项的默认锚点 | 工程 |
| 画布 | object | {宽, 高, 适配};尺寸取资产规格数据,不即兴 | 工程 |
| 状态 | enum | 草稿 / 已定稿 / 已作废 | 策划端 |
| 元素 | array | 见下 | 见下 |
| schema版本 | string | 入库时的合并 schema 版本 | 工程 |

**「已定稿」不是需求状态机的一档。** 需求状态机保持
`草稿 → 已确认 → 进行中 → 待验收 → 已完成` 不变;界面定稿是工作项内部的关卡。
需求状态机越少档越好,往里塞美术流程会让引擎跟着一起复杂。

## 四、元素级字段(按类型给模板)

字段**不是全量固定**的:Button 必须写清交互与失败,纯装饰件写这些毫无意义。
每类元素必填哪些、选填哪些,由**元素类型模板**说了算——那是规则数据,走规范分层
(`Specifications/{Baseline,Project,Business}/ui-element-template.*.json`),
加一类元素 = 加一条数据,不改引擎。

全字段池(模板从中挑):

| 字段 | 说明 |
|---|---|
| id | PascalCase,**同时是 C# 标识符**——缩写会被命名门禁拦(写 Button 不写 Btn) |
| 名称 | 人话名字 |
| 类型 | Button / Label / Image / ProgressBar / Container / Decoration / … |
| 父容器 | 元素 id;顶层为空 |
| 布局 | {锚定, 位置, 尺寸} |
| 复用 | `本界面专有` / `通用`;通用件落 `Art/Texture/Ui/Shared/`,先查库再决定出不出图 |
| 重复 | 同款几个(格子、列表行);**只出一张图**,其余是同一资产的实例 |
| 初始态 | {显示, 可用, 默认值} |
| 前置 | {条件, 不满足: 灰掉/隐藏} |
| 状态 | 常态/悬停/按下/禁用/选中/加载中,各自长什么样 |
| 交互 | [{事件, 动作}];事件:点击/长按/拖拽/双击 |
| 数据 | {来源, 刷新时机} |
| 成功 | 做完之后界面怎么变 |
| 失败 | **数组**——一种失败一条 {条件, 提示, 处置} |
| 边界 | 空列表/超长文本/数值上限/快速连点 |
| 动效 | {进场, 退场, 反馈};每条 {类型, 时长ms, 缓动, 可打断} |
| 音效 | {点击, 成功, 失败} |
| 验收 | **一句可测的断言**,进需求的验收核对表 |

两条硬规矩:

1. **「失败」是数组,不许写成一句话。** 「背包满了」「钱不够」「网络断了」
   三条的文案与处置完全不同,合成一句「失败提示」等于没写,
   而程序照着这句写出来的就是三种失败一个提示框。
2. **「验收」必须可测。** 「动效要流畅」不可验收;
   「进场 200ms、ease-out、可被点击打断」可验收。写不出可测的断言,
   说明这条需求还没想清楚——那正是这一层该拦住的东西。

## 五、三个生成物

### 5.1 布局图(白块)

**从规格确定性渲染,不由模型画。** 一个元素一个白块,块上标 id 与类型,
按 `布局` 的坐标尺寸摆位。

为什么不让模型画:模型画的图**不可复现**、改一处要重画全图,
而且图上画的与规格里写的会漂——拆图那块已经吃过这个亏。
确定性渲染让「布局图与规格一致」成为结构保证而不是纪律:
改规格即改图,重跑无 diff(幂等门禁查)。

布局图有两个用途:给策划确认功能位齐不齐,给美术当底稿。
它**不追求好看**——追求好看的是美术稿,那是下一步的事。

### 5.2 uidef

从元素清单生成:id、类型、父子、布局直投;贴图路径在美术定稿之后回填。
uidef 归工程所有(贴图、布局、元素类型),界面规格归策划所有(行为、成败、验收)——
**两份分开是因为写入者不同**:美术换贴图不该动策划写的行为规格
(总纲 §一「写入者唯一」纪律)。

### 5.3 资产清单

元素清单去掉「不需要图」的(Container、纯逻辑件),按 `复用` 与 `重复` 收敛:

- 通用件 → 先查 `Art/Texture/Ui/Shared/`,命中就复用,**不新建资产请求**;
- 重复件 → 只出一张,其余记「同款 ×N」;
- 剩下的才生成资产请求(域=资产.生图)。

一屏从「画面上能框出来的 100 多个」收敛到「真正要出的 15~25 个」,
靠的就是这一步——而不是靠给切图算法加阈值。

### 5.4 回模块策划案

界面规格要回写进这个模块的策划案(`Pools/Designs/Modules/<模块>/index.md`)——
元素行为表进它的生成区、布局图进它的 `media/`。**怎么回、为什么是模块层而不是需求层**,
写在 `Specifications/Baseline/planning-doc.baseline.md` 里,不在这儿重复一遍。

需求案那边只留**一行指针**。出完功能图与每次需求验收都会自动重渲一次。

## 六、与拆图的新关系

拆图从「看图猜元素」改成「照清单切」:

1. 界面规格给出元素清单与每个元素的布局矩形;
2. 拆图拿这份清单去美术稿上取对应区域(**不再让视觉模型自己找元素**);
3. 视觉模型只负责一件它真正擅长的事——把那一块抠成干净的透明底单图。

好处是职责分干净了:框错了是规格写错了(人改规格),抠差了是模型的事(重抠)。
从前这两件事混在一起,出了问题指不到人。

**助手那颗拆图按钮走的就是这条路。** 判定链是「会话 → 需求 → **模块** → 界面规格 → 资产清单」:会话在做哪条需求有留底,
需求的「专项」就是模块,按模块找规格——**不按需求找**:这条需求可能只改了一个按钮,
而要切的是整屏,它多半是更早那条需求出的。三种情形各有各的态度:

- **一份规格** → 照清单切,清单外的框丢掉、清单里没找到的如实报;
- **没有规格** → 退回看图猜,**并在流水里写明走的是哪条路**:两条路的产出看着一样,
  可信程度差着一整层;
- **好几份规格** → 停下来问是哪一屏,不挑一屏赌。人回「商店那屏」或「UI-0002」就能接着走——
  **问出来的问题要答得上才算问**。

模块名也跟着改由规格给(面板名),不再让标框的模型顺带猜:
面板名是确定的,还决定 uidef 名与图集,而猜出来的每趟都可能不一样。

## 七、门禁挂钩

| 门禁 | 查什么 |
|---|---|
| 界面规格校验 | 过合并 schema;元素 id 唯一、父容器存在且无环;按元素类型模板查必填 |
| 验收可测 | 每个元素的「验收」非空;「失败」是数组 |
| 布局图幂等 | `_Generated/Interfaces/*.layout.svg` 重渲无 diff |
| uidef 一致 | uidef 的元素集合 = 界面规格的元素集合(允许贴图路径为空) |
| 元素 id 合规 | 不含命名门禁黑名单里的缩写——它会原样变成 C# 标识符 |
| 资产归属 | 资产请求的落点模块 = 界面规格的 `面板`;通用件落 `Shared/` |

## 八、还没定的

- **其他模块的粒度模板**(2D 动画、3D 模型与动作、角色设计、特效、音频、场景):
  结构照抄本文(全字段池 + 按类型给模板 + 每条可测),UI 跑通了再扩。
- **界面规格由谁产**:AI 产草案策划审,还是策划直接写。倾向前者,
  但要等方案阶段真接起来才好定。
- **改了界面规格如何标脏下游**:应当复用「打断重规划」(总纲 §五横切 A),
  但映射关系(改哪个元素脏哪个资产)还没写。
