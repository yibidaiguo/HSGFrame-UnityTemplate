# 创作管线 · P2 批次 2「资产规格」日志

> 总账在 [创作管线进度](../creation-pipeline-progress.md)。本文只装这一批的落地记录与验收证据。

## 这一批真正做的是什么

子文档 06 §一 有一句话是整条美术管线的地基：

> 规格与落点**不由 AI 即兴**——由资产规格数据按资产类型给默认，brief **只能收紧不能放宽**。

批次 1 做完时这句话还没落地：`art.request` 的 `规格` 是空字典、`落点` 是命令行随便传的。
这一批把它做成机器。顺带铺出了 `规范/` 的三层目录——在此之前那儿只有三份结构规范文档。

## 「收紧 / 放宽」是本批最难的一处，因为文档没定义它

子文档 07 §二 只写了「收紧任意，放宽仅限上层标了『可覆盖』的键」，
**没说什么叫收紧**。这一批把它钉死成三条可执行规则：

| 值的类型 | 判定 |
|---|---|
| 数字 | 新值 `<=` 旧值算收紧，`>` 算放宽 |
| 布尔 | `false → true` 算收紧（多一条要求），`true → false` 算放宽 |
| 字符串等其余 | **一律算放宽** |

第三条是刻意的：改字符串等于换了一套要求，说不清是松是紧。**判紧就会开出一个谁都能钻的口子**
（把 `格式` 从 `PNG` 改成 `JPG` 也叫收紧？），所以宁可误伤——要覆盖就去基线的 `可覆盖` 里显式登记。

另外：**放宽的值不采纳（保留旧值）但合并继续走完**，一次跑出全部问题，
而不是撞上第一个就停——门禁一次报全比来回跑三趟有用。

## 执行后端这一轮报上来的两件事（都属实，一件是我任务书写错）

1. **`Module` 参数穿不通**——**这是我任务书的错**。任务书给的 `Inspect(string, string)` 签名
   没有 module 参数，于是 `art.request` 用带业务层的数据建请求、自检却用不带业务层的数据校，
   业务层一改落点就会把刚建好的请求删掉。它**照任务书字面实现并把这处出入如实报了上来**，
   没有自己改签名。已由 Claude 把 `moduleName` 一路穿通（含 7 处测试调用点）。
2. **`Values` 里三个顶层键存去引号文本而非原始 JSON 文本**——任务书说「一律存原始 JSON 文本」，
   但 `落点` / `命名模式` / `域` 若带引号，会把 `"Assets/..."` 连引号写进资产请求。
   它改成去引号并说明了理由。这个改动是对的。

## 已知缺口（不阻塞，记着）

- **`风格锚点` 仍是空字典。** 子文档 06 §一 说它缺省取所属专项的「默认锚点」——
  那要先有专项的默认锚点字段，属批次 4。
- **门禁只核对资产请求，不核对真实资产文件。** 子文档 07 §三·一 的「资产规格」检查器
  还要查「落点资产 × 规格数据 + 边车存在且合法」，那要等真有资产落地（批次 3 之后）。
- **`规范/业务/<模块>/` 的模块名没有对着模块注册表查**（子文档 07 §一 要求「业务目录名必须
  对应已注册模块，门禁查，防拼错」）。目前拼错只会静默不生效。
- **数字比较用的是 `decimal` 语义的大小**，没有「哪些数字是越大越严」的概念
  （比如「最小尺寸」这种键，变大才是收紧）。基线里目前没有这类键，真要加得先想清楚。
