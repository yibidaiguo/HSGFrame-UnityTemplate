# 设计库(创作管线子文档 09)

> 状态:草案 · 2026-08-23
> 上游:总方案 §三(设计池);相邻:子文档 01(池子格式)、06(美术管线)、08(界面规格)。
> 本文把原来那个「一个设计池」拆成**两个库 + 一份资产索引**,并定分层分模块的规矩。

## 一、现在为什么不够

`Pools/Designs/` 眼下是三样混装:`Records/`(记录)、`Digest/`(汇总)、`Final/`(风格定稿)。
三个缺口:

1. **美术与策划混在一个池子里。** 「断签从第 1 天重计」和「UI 图标一律 Q 版」
   是两种完全不同的东西:前者是玩法事实,后者是外观约束;读者不同、改的人不同、
   过期的方式也不同。堆在一起,两边都得从一堆不相干的条目里筛自己那部分。
2. **没有模块层。** 记录只有一个 `模块` 字段,定稿是全局的。
   于是「背包偏冷、商店偏暖」这种模块级差异没有落点,要么写成全局(污染别的模块),
   要么写在需求里(下次没人找得到)。
3. **没有「已经做过什么」的索引。** 这一条最贵:
   美术每出一张图都是从**零**开始理解风格——配方里那几句提示词就是它知道的全部。
   同一个项目的第 5 个界面和第 1 个界面之间没有任何机器可读的联系,
   风格靠人盯着,盯漏了就跑偏。**「参考已有资产」现在只是一句口号,机器上没有落点。**

## 二、两个库

```
Pools/Designs/
  Game/                     ← 策划设计库:这个游戏是什么样
    <模块>/records/DR-xxxx.json     只追加的决定账本
    <模块>/digest.md                生成物:该模块的当前设计(余额)
    glossary.json                   术语表:同一个东西不许两个叫法
  Art/                      ← 美术设计库:这个游戏长什么样
    project/final.json              项目级定稿:世界观、主色、材质语言、负面清单
    <模块>/final.json               模块级定稿:只能在项目级里**收紧**
    <模块>/refs/                    参考图(本体),被 md 与配方引用
  Interfaces/UI-xxxx.json   ← 界面规格(子文档 08)
  library.json              ← 资产库索引(生成物,见 §四)
  conflicts.json
```

**策划设计库 ≠ 需求池。** 这条最容易混,写死:
需求池装**要做什么**(一次性的事,做完就完了);策划设计库装**这个游戏是什么**
(长期事实,一直有效)。「做一个背包」是需求,「背包上限 40 格」是设计库。
判据:这句话在需求做完之后还成不成立?成立就进设计库。

## 三、分层与分模块

### 三层,子级只能收紧

```
项目级   世界观、主色、材质语言、全局负面清单        ← 一个项目一份
模块级   这个模块的偏移(背包偏冷、商店偏暖)          ← 只能在项目级里收紧
资产级   单张资产的具体规格                          ← 资产请求
```

**「只能收紧」是这一层的核心约束**,与规范分层同一套语义(总纲 §九):
模块可以把项目色板的 8 色缩到 3 色,不能引入项目色板之外的颜色;
可以在项目负面清单上再加几条,不能删掉上面的。想引入新色 = 改项目级定稿,
那是一次显式的、要走审查的动作——**风格跑偏几乎总是从「就这个模块特殊一下」开始的**。

### 模块名必须是同一套

模块名在四处出现,**必须逐字一致**:

| 出现在 | 形态 |
|---|---|
| 策划设计库 | `Pools/Designs/Game/<模块>/` |
| 美术设计库 | `Pools/Designs/Art/<模块>/` |
| 界面规格 | 面板级字段 `面板` |
| 资产落点 | `Art/Texture/Ui/<模块>/`、`Specifications/Business/<模块>/` |

不一致的话这四处各叫各的,串不起来——查「背包的风格定稿」查不到、
出图时取不到模块色板、改了定稿也列不出受影响的资产。
门禁按这条对账(§六)。命名用 **PascalCase ASCII**(决策 1:全仓路径只许 ASCII)。

## 四、资产库索引(这一条是「不重新设计风格」的机器实现)

```json
// Pools/Designs/library.json —— 生成物,由 library.rebuild 从溯源边车与落点扫出来
{
  "契约版本": "1.0.0",
  "资产": [
    {
      "id": "ASSET-0042-01", "命名": "T_ButtonSort",
      "资产类型": "UI元素", "模块": "Inventory", "复用": "通用",
      "落点": "Assets/Game/Art/Texture/Ui/Shared/T_ButtonSort.png",
      "主色": ["#2b3a4a", "#7f8fa6", "#d9e1ea"],
      "定稿": "UI风格@v3", "来源需求": "REQ-0042", "来源界面": "UI-0007",
      "产出时间": "2026-08-23T10:00:00Z"
    }
  ]
}
```

索引是**生成物**(扫溯源边车 + 落点算出来,幂等门禁查),不是手写账本——
手写的账本迟早跟磁盘上的实际资产对不上,而对不上的索引比没有索引更糟。

出图前那一步因此变成三查,顺序固定(库里全空时走[子文档 10](10-direction-and-reading.md)的冷启动):

1. **查同名**——`Shared/` 或本模块里已经有这张(子文档 08 §5.3),命中就复用,不出图;
2. **查同类**——同模块、同资产类型的已有资产,取最近的 N 张(默认 3)当**风格参考图**;
3. **取模块定稿**——色板与负面清单进提示词。

第 2 条是关键,也是眼下完全没有的那条:
**光有色板文字,模型出来的东西仍旧会飘**——「低饱和冷色系」这六个字,
一百个模型有一百种理解。把同模块已有的三张真图发下去,风格才接得上。
配方那边已经有「参考图」锚点槽(子文档 06 §一),这里只是把它填上。

出完之后反过来对账:

4. **算离风格距离**——新资产主色聚类 vs 模块定稿色板的最小距离和;
   超阈值报**软黄**进验收报告(不拦,拦了会挡住合理的例外),
   连续多张超标才值得怀疑定稿本身。这是把 §六 的「离风格报告」从事后前移到出图时。

## 五、md 文档只放引用,本体在池子

设计库里的文档(digest、需求文档、界面规格的说明段)**只写指针,不塞本体**:

| 写法 | 指向 |
|---|---|
| `[[DR-0107]]` | 策划设计记录 |
| `[[UI-0007]]` | 界面规格 |
| `[[ASSET-0042-01]]` | 已产资产(索引里那条) |
| `[[STYLE:UI风格@v3]]` | 美术定稿的某个版本 |
| `[[REF:Inventory/refs/mood-01.png]]` | 参考图本体 |

三个理由:① 图片本体进 md 会让文档变成二进制黑箱,git diff 看不见改了什么;
② 同一张参考图被三份文档引用时,拷三份必然有一份先过期;
③ 引用可以被门禁查——指到不存在的实体当场红,而一段文字里写「参考背包那个风格」
谁也查不了。

**门禁查每个引用能不能解析到实体**(§六)。这条是「保持一致」能靠机器兜住的部分:
删掉一份定稿、改了个 id,所有引用它的文档立刻变红,而不是等到半年后有人点开发现图没了。

### 五·一、模型与动画:本体不进知识库,只进设计图

同一条规矩在模型与动画这两类上有个更硬的说法:**本体一个字节都不往知识库推**,
推上去的只有**设计图**——

| 类别 | 进知识库的 | 留在仓库的 |
|---|---|---|
| 模型 | 效果图、三视图(`art.views` 出的那张) | `.glb` / `.fbx` / 贴图 |
| 动画 | 帧序列示意(`anim.assemble` 出的那张横排图集) | 逐帧 PNG、clip、图集本体 |

三个理由与 §五那三条同源,但第一条要重得多:模型与动画的本体是**几十上百兆**的二进制,
知识库既存不动也搜不了,人在那儿点开一个 fbx 得到的只是一次下载。
他去知识库要看的是「长什么样、动起来什么样」——那正是三视图与帧序列示意回答的问题。

落点分两侧,沿用台账里那两个键:动画与模型这些**美术侧**的走
`美术设计库文档`(`_Generated/DesignLibrary/art.md`),策划侧走 `策划设计库文档`。
一份文档两种读者的老毛病见 §二。

## 六、门禁挂钩

| 门禁 | 查什么 |
|---|---|
| 设计库分层 | 模块级定稿只收紧不放宽(色板 ⊆ 项目色板;负面清单 ⊇ 项目负面清单) |
| 模块名对账 | 四处出现的模块名逐字一致;不一致列出差在哪 |
| 资产索引幂等 | `library.json` 重扫无 diff |
| 索引新鲜度 | 落点里有、索引里没有(或反之)判红——对不上的索引比没有更糟 |
| 引用有效 | md 里每个 `[[…]]` 都能解析到实体 |
| 术语一致 | 需求与设计文档里出现的术语在 `glossary.json` 里;同义词只许有一个正名 |
| 离风格(软黄) | 新资产主色与模块定稿色板距离超阈值,进验收报告不拦 |

## 七、我补的几条(原话里没有,但缺了会漏)

1. **术语表**(`glossary.json`)。同一个东西两个叫法是需求文档最常见的跑偏:
   「背包/仓库/储物格」混着写,需求校验查不出矛盾,助手也会跟着乱用。
   一个词一个正名 + 同义词列表,需求入池与助手回话都读它。
2. **反向引用**。改了模块定稿要能立刻列出「该模块下哪些资产是照旧版出的」——
   这是「打断重规划」在美术侧的对应物(总纲 §五横切 A)。索引里存了 `定稿` 版本号就够算。
3. **定稿升版不自动重出**。列出受影响资产、标脏,但**不自动重跑**——
   一次定稿升版可能波及上百张图,自动重跑等于自动烧钱。人挑哪些重出。
4. **负面清单要能继承与叠加**。项目级写「不要赛博朋克霓虹」,模块级再加
   「背包里不要出现武器」;取用时是并集。只让模块级覆盖的话,
   一个模块的疏忽就能把项目级的约束整条丢掉。
5. **参考图也是资产**,要进索引、要有溯源。今天参考图散在配方目录与聊天记录里,
   换个人接手根本不知道当初照着什么画的。

## 八、还没定的

- **主色聚类算什么**:k-means 8 色是子文档 06 定的,离风格距离用哪种色差公式
  (CIEDE2000 还是简单欧氏)没定。先做欧氏,不准再换——这一条只是软黄。
- **同类参考图取哪 N 张**:最近产出的?人工标了「代表作」的?
  倾向后者(定稿时顺手标),但要等索引真跑起来才好定。
- **策划设计库的记录粒度**:现在是一条决定一个 JSON,模块多了之后会不会太碎,
  要不要按主题合并——先跑,碎了再说。
- **3D/动画的设计库形状**:本文的三层与索引对贴图成立,
  对模型(面数/骨骼/材质槽)与动画(帧事件/可打断窗口)要各自加字段,
  照 UI 这条跑通了再扩。
