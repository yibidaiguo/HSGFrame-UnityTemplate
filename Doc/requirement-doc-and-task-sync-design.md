## 一、要解决的是什么

现在需求在池子里是一份 JSON（`Pools/Requirements/REQ-0042.json`），飞书那边只有一张多维表格。
两个后果：

1. **人看不了。** 一条需求的完整表述（背景、玩法、边界、配图）塞不进表格单元格，
   而仓库里的 md 要有人 clone 了仓库、开着编辑器才看得见。策划看不到自己提的需求长什么样。
2. **AI 拿不到全貌。** 表格字段是扁的，「为什么这么设计」「哪些明确不做」这类
   决定实现走向的信息没有地方落，于是每次开发都要重新问一遍。

要加的东西一句话：**需求要有一份正经文档，两侧都能看、都能改，但任何时刻只有一侧说了算。**

## 二、结论先写：七件事各落在哪

| 用户要的 | 落法 | 批次 |
|---|---|---|
| 1. 自定义需求文档 | 需求目录化后手写 `index.md`，与自动生成的走同一套规范、同一道门禁 | A / B |
| 2. 聊完自动生成文档 | 助手 `assist.serve` 产文档草稿；触发有两条路：**说一句**（口令）或**点卡片按钮** | C |
| 3. 两个同步方向 | `doc.approve`（飞书 → 项目，批准后 AI 开工）与 `doc.push`（项目 → 飞书，只读镜像） | D |
| 4. 文档规范，AI 优先、能放图放视频 | `Specifications/Baseline/requirement-doc.baseline.md` + `gate.reqdoc` | B |
| 5. 不自动同步、人能改、同步时 AI 规范化 | 草稿只落暂存区；`doc.normalize` 在同步那一刻跑，产 diff 给人看，不静默改 | C / D |
| 6. 任务能点超链接看对应文档 | 任务表与面板任务卡都带「需求文档」列，指向 wiki 节点链接 | E |
| 7. AI 开发时自动建任务、状态同步到飞书 | 工作项落队即 upsert 一行到飞书任务表，状态变化走既有出站通道 | E |

## 四、需求目录化：影响面与迁移红线

**这是本次唯一一处破坏性改动**，先把账摆清楚。

现状 `Pools/Requirements/REQ-0042.json` → 新形状：

```
Pools/Requirements/REQ-0042/
  requirement.json      ← 原来那份，一个字段不动
  index.md              ← 需求文档正文
  media/                ← 图片与视频本体
  snapshots/            ← 覆盖前留底：doc.v1.md、doc.v2.md……
```

要改的地方（已实测清点）：

| 类别 | 处数 | 具体 |
|---|---|---|
| 拼 `<id>.json` | 8 | `PoolPushPlanner:89`、`RequirementIntake:189/216`、`TaskStatusReport:25`、`CreationPanelReader:2964` 等 |
| 枚举需求文件 | 3 | `RequirementIntake:249`（`*.json`）、`ConflictDetector:87`（`REQ-*.json`）、`CreationPanelReader:1402` |
| 取号 | 1 | `IdentifierAllocator.Next` 现在扫**文件名**，要能扫**目录名** |
| 校验 | 1 | `RequirementValidator.CheckDirectory` 的「文件名与 id 一致」改成「目录名与 id 一致」 |
| 测试 | 6 个文件 | `PoolTestWorkspace` 是总闸，改它能带走大半 |

**红线三条：**

1. **路径不许再散着拼。** 迁移的同时把 8 处收进 `PoolPaths` 的四个新访问器
   （`RequirementDirectory` / `RequirementFile` / `RequirementDocument` / `RequirementMediaDirectory`），
   以后加东西只改一处。**只搬不收等于把同一个坑挖深。**
2. **改测试断言是单独一步**（铁律 3）。目录化会动一批断言，那批走单独提交、带 `[测试变更]`。
3. **`gate.pathascii` 仍然管着**：`REQ-0042` / `index.md` / `media/` 全 ASCII，媒体文件名也是——
   而资产名归一化器现在产中文名（待办账本第 1 条末节那笔没销的账），
   **媒体入库要走 ASCII 归一，不许复用那个归一化器**。

## 九、批次拆分

| 批 | 内容 | 能独立验吗 | 风险 |
|---|---|---|---|
| **A** | 需求目录化迁移 + `PoolPaths` 四个访问器 + 取号器扫目录 + 校验改判目录名 + 测试 | 能（秒级门禁） | 破坏性，但纯本地，不碰飞书 |
| **B** | 文档规范基线 + `doc.render` + `gate.reqdoc` | 能 | 低 |
| **C** | 助手产文档草稿 + `doc.normalize` + 旁路认卡片回调 + 口令 | 卡片那半要真点一次 | 3 秒时限、新目录 |
| **D** | 飞书桥加 `doc.push` / `doc.pull`：wiki 建节点、md→块转换、图片上传回填、快照 | **必须真跑**（决策 91） | 外部 API，形状要拿真回包核 |
| **E** | 任务表建表 + 工作项出站 + 需求级汇总 + 面板与任务表的文档链接 | 真跑 | 中 |

**依赖**：A → B → C；D 依赖 B（要有规范才知道推什么）；E 依赖 A 与 D（要有链接才填得进列）。

## 十、环境：办到哪一步了（2026-08-21 实测）

| 事项 | 状态 | 凭据 |
|---|---|---|
| `docx:document` | ✅ 生效 | 读块接口 `code=0` |
| `docx:document.block:convert` | ✅ 生效 | 真转过一段 md，回 2 个块（类型 3 标题 / 2 正文） |
| `wiki:wiki`（节点级） | ✅ 生效 | `get_node` 解出了节点信息 |
| **知识空间级权限** | ❌ **被拒** | 空间信息与一级节点列表都回 `131006 wiki space permission denied, tenant needs read permission` |
| 卡片回调订阅 | 待验 | 要等真点一次按钮 |

**两条实测结论：**

1. **`GVZhwfIy6iFFZqkEbqocNRgTnvc` 是节点 token，不是 `space_id`。**
   真正的 `space_id` 是 `7676450654847503634`（`obj_type=docx`、一级节点、标题「首页」）。
   地址栏里 `/wiki/` 后面那串永远是节点 token——**这个坑要写进配置文件的注释**，已写。
   两者都进了 `local.json`：`知识空间标识` 与 `需求文档父节点`。

2. **应用能读那一个节点，但在空间里没有身份。** 所以 `wiki:wiki` 这个权限
   开了不等于能建节点——**空间成员资格不归开发者后台管**，要在飞书的知识库设置里
   把应用加成成员（至少可编辑，建节点要管理员）。这一条不办，D 批第一步就会 `131006`。

**转换接口还额外送了一样东西**：返回体里有 `block_id_to_image_urls`，
图片那步比原设计省事——不用自己从 md 里扒图片路径再逐个对齐块。

## 十一、要立的新决策（编号接 98）

99. 需求从「一文件」改成「一目录」，路径一律经 `PoolPaths` 访问器，不许散拼。
100. 需求文档任何时刻只有一侧有写权，权威侧写在 frontmatter 里，随文档走。
101. 覆盖对侧内容之前必须留快照——静默覆盖吞掉的是人的字。
102. AI 产出的文档一律先进暂存区，同步是人点的；同步那一刻跑规范化，产 diff 不静默改。
103. 卡片回调只许「秒回 + 落信号」，判定放到消费者里；新消费者给新目录（决策 95 的推论）。
104. 按钮与口令必须进同一个处理函数。
105. 任务行在工作项**落队**时建，不在跑完时建。
