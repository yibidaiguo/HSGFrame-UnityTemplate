# Luban 工具来源

`ITablePipeline` 的第二个实现（`LubanTablePipeline`）要用 Luban 的命令行工具。
它约 6 MB / 197 个文件，**按 `.gitignore` 的约定不进仓库**——
与 HybridCLR 同一手法：第三方工具链按需取，仓库里只留取它的办法与版本号。

| 项 | 值 |
|---|---|
| 版本 | v4.11.0 |
| 上游 | https://github.com/focus-creative-games/luban |
| 发布物 | `Luban.7z`（官方只发 7z，Windows 自带的 tar 解不了它） |
| 取它 | `pwsh -NoProfile -File ./取工具.ps1` |

取完之后 `Tools/Luban/Luban.dll` 就位，用这一条自检：

```bash
dotnet Tools/Luban/Luban.dll --help
```

## 为什么不进仓库

阶段 3 的日志里记着一条判断：接不接 Luban 需要人拍板，
因为「自研 schema.json + Scriban 链路」与「Luban」是两条并存的链路。
人在 2026-08-15 拍板要接，于是有了第二个 `ITablePipeline` 实现。
两条链路都保留：`config.generate` 的 `PipelineName` 参数决定走哪条。

工具本身不进仓库的理由与 HybridCLR 那 819 MB 是同一条——
第三方产物落进版本库之后，升级它就变成一次大 diff，而它本来只是一个可重新取得的外部依赖。
