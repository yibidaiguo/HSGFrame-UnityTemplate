## 二、为什么是 Python 旁路

飞书的长连接没有官方 .NET SDK，自己实现那套私有 WebSocket 协议不划算。
**关键在于旁路的输出接口就是一个文件**——接的是 P8 批次 1 已经做好的文件唤醒源
（决策 82）。所以这个进程崩了、换了、以后有人用 C# 重写，**引擎侧一个字都不用改**。

长连接相对回调地址的好处：**不需要公网 IP**，本机 NAT 后面也能收事件。

- 落点：`Bridges/feishu/scripts/wake_sidecar.py`（driver 特有的东西住在桥里，决策 84、93）
- 运行环境：`D:/Tools/FeishuWake/.venv`（`lark-oapi`），**不进仓库**
- 密钥从 `local.json` 读，**只进 SDK 构造参数，不打印不写日志**（决策 5、78）
- **旁路不做任何判定**，只把事件原样落成信号（决策 81：外壳不做判定）

## 三、已知缺口：多维表格记录变更事件没通

**管线真正想要的那个事件**（`drive.file.bitable_record_changed_v1`）**没收到**。

实测过程：

1. 调 `POST /drive/v1/files/{token}/subscribe?file_type=bitable` → 先是缺 scope
   （`99991672`），用户补了 `docs:event:subscribe` 之后变成 **`1069603 forbidden`**——
   **换了个拒绝理由，不是同一个问题**。
2. 不调订阅接口、直接往「需求」表写一条记录（`code=0` 真写进去了），
   **等 10 秒，唤醒目录没有新信号**。测试记录已删。

所以：**长连接与事件投递本身是通的**（消息事件证明了），
**但表格记录变更这一路还差一层飞书侧的设置**，`1069603` 具体缺什么没查出来
（官方文档页是 SPA，抓不到正文）。

**下一个接手的**：从 `1069603` 这个码入手，怀疑方向是
「应用要是该文档的所有者/管理员」或「Bitable 的记录变更事件另有订阅入口
（不走 drive 的 subscribe）」。**别从 scope 方向查**——scope 那一关已经过了。
