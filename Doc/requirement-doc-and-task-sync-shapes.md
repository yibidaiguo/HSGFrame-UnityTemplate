### 5.2 为什么这么定——三条都是给 AI 定的

1. **章节标题是契约，不是排版。** 名字与顺序由基线固定，AI 定位靠标题，不靠猜段落语义。
   缺了必填小节 = 门禁红，不是「凑合能读」。
2. **机器要读的东西一律结构化。** 需要判定的字段进 frontmatter；
   验收标准必须是**有序列表、一条一句、单条可判真假**——阶段 4 是逐条核的，
   一条里塞三件事就核不动。散文写的验收标准由 `doc.normalize` 提成列表，提不动就打回。
3. **AI 看不见图，但看得见说明。** 所以媒体在 frontmatter 里**必须带说明**，
   而且说明要写「图里有什么」而不是「这是一张图」。这条是「优先 AI 友好」在媒体上的全部含义。

### 5.3 图与视频怎么落

| | 仓库侧 | 飞书侧 |
|---|---|---|
| 图片 | `media/*.png`，md 里相对路径引用 | 转成 docx 图片块（先建块 → 以块 id 为 parent 上传素材 → `replace_image` 回填） |
| 视频 | `media/*.mp4` | **附件块 + 链接**。docx 有没有原生视频块，实现时必须拿真回包核一次，不许凭印象（决策 94） |
| 大文件 | 超过阈值不进仓库，只在 frontmatter 记外链 | 同左 |

### 5.4 门禁 `gate.reqdoc`

查六条：frontmatter 必备键齐全 → `需求id` 与目录名一致 → 必填小节按序在位 →
验收标准非空且是有序列表 → 媒体引用的文件真存在且 ASCII 名 → 生成区没被手改（比对 hash）。

## 六、两个同步方向与权威侧翻转

```
                    ┌──────────── 权威侧 = 飞书 ────────────┐
策划聊天 ──→ assist.serve 产草稿 ──→ 暂存区 _Tasks/docdrafts/
                                        │（不自动同步）
                        人在飞书里改 ←──┘ 人点「同步进项目」/ 面板点批准
                                        │
                          doc.normalize（AI 规范化，产 diff 给人看）
                                        │  gate.reqdoc
                                        ↓
                    ┌──────────── 权威侧 = 项目 ────────────┐
        落 Pools/Requirements/REQ-0042/index.md + 锁定 + 状态=已确认
                                        │
                        入队 → AI 开工（既有引擎）
                                        │
                          doc.push（只读镜像，覆盖飞书节点）
```

四条命令：

| 命令 | 方向 | 允许条件 | 干什么 |
|---|---|---|---|
| `doc.render REQ-0042` | — | 任意 | 按需求 JSON 生成/刷新文档骨架与生成区 |
| `doc.normalize REQ-0042` | — | 任意 | 执行后端读文档 → 补小节、提列表、回填 frontmatter、登记媒体；**产 diff，不静默落盘** |
| `doc.approve REQ-0042` | 飞书 → 项目 | 权威侧=飞书 | normalize → 门禁 → 落盘 → 锁定 → 权威侧翻到项目 → 入队 |
| `doc.push REQ-0042` | 项目 → 飞书 | 权威侧=项目 | 覆盖 wiki 节点内容；**覆盖前把飞书侧现状拉回来存 `snapshots/`** |

**为什么覆盖前要留快照**：镜像期人仍然可能在飞书上改（我们拦不住，也不该拦）。
静默覆盖等于吞掉别人的字。留一份快照 + 在回话里说一句「你在飞书上的改动已存为 doc.v3.md」，
成本一份文件，换的是这套东西没人敢用/敢信的那个风险。

**权威侧写在 frontmatter 里，不写在别处**——它跟着文档走，clone 下来就知道现在谁说了算。

## 七、触发：说一句，或点一个按钮

### 7.1 卡片按钮（已核实可行）

新版卡片回调 `card.action.trigger` **支持长连接**（旧版「消息卡片回传交互」不支持），
所以不需要公网回调地址，与现有旁路同一条连接。约束：**3 秒内必须应答**。

因此旁路的处理必须是「秒回 toast + 落信号文件」，**一个字的业务判定都不许放在回调里**
（决策 81：外壳不做判定）。信号落 **`_Tasks/cardactions/`**——
按决策 95 的推论，新消费者给新目录，不许往 `wake/` 或 `conversations/` 里挤。

聊完之后助手发的卡片带三个按钮：**生成需求文档** / **同步进项目** / **打回重聊**。

### 7.2 口令

同一批动作也认文字口令（「生成需求文档」「同步进项目」）。
两条路进同一个处理函数，**不许各写一套**——否则按钮与口令的行为迟早分叉。

## 八、任务表：AI 一开工就有行，状态跟着走

飞书侧新增一张**任务表**（bitable，与需求表同一个多维表格）：

| 列 | 来源 | 谁写 |
|---|---|---|
| 任务id（WI-0042-03） | 工作项 | 工程 |
| 需求id | 工作项 | 工程 |
| **需求文档** | wiki 节点链接 | 工程 |
| 标题 / 域 | 工作项 | 工程 |
| 状态（待执行/执行中/待审/完成/标脏/挂起） | 工作项 | 工程 |
| 开始时间 / 完成时间 / 产物 | 引擎 | 工程 |

- **建行时机**：工作项落队那一刻，不是跑完之后——「需求和任务对不上」正是因为行建晚了。
- **幂等**：按任务 id upsert，重投不产重复行（与 `bridge.push` 现有幂等同源）。
- **状态同步**：工作项状态一变就出站，走既有 `pool.push` 通道扩一个事件，不新开链路。
- **需求级汇总**：需求表加「进度」（`3/7`）与「当前阶段」两列，每次工作项状态变化重算。
- 建表仍走 `bridge.apply`，**只加列不改类型不删列**（决策 96）；
  数组/对象列要带「逻辑类型」（决策 97）。

面板的任务卡放同一个链接，指向同一个 wiki 节点——**链接只有一个来源**（frontmatter 的 `同步.链接`）。
