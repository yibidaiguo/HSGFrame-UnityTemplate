## 二、怎么接的：两条队列，一个消费者

```
飞书消息 → 长连接旁路（归一成「会话」块）→ _Tasks/会话/*.json
   → assist.serve 一轮：读消息 → 执行后端 → 补齐工程字段 → req.validate
   → 回话（bridge reply）→ 校验过且开了开关才写下游 → 投唤醒信号 → 引擎醒
```

**唤醒目录与会话目录刻意分成两个**（新决策 95）。原来消息事件也落唤醒目录，
但那样一来引擎守护与助手会话是**两个消费者盯同一个队列**——谁先归档谁赢，另一个永远收不到。
现在消息只进会话队列，助手**真建出草稿之后**自己往唤醒目录投一条信号，
链路接得上，而且比原来更准：没建东西就不叫醒引擎，省得它白跑一轮。

归一（chat_id / open_id / message_id / 正文）放在**旁路**里做，不在引擎里做——
事件长什么样是下游特有知识（决策 93）。引擎只读「会话」块，换个消息下游零改动。

`assist.serve` 与引擎守护同构：**有限轮**，`--max-rounds 0` 才是无限（决策 81）。
信号在这一轮全部跑完之后才消费（决策 82）。

## 三、真跑撞出来的三个 bug——都是「测试全绿而那条路根本走不通」

**这一批真正的收获在这里。** 三个 bug 单测一个都测不出来，因为它们都在
「引擎产出的合法数据」与「下游表能接受的形状」之间的缝里。

### bug 1：分类型必填的字段根本没有列

`table-description.json` 的「表单」里摆着 `目标 / 玩法 / 现状 / 期望 / 复现步骤 / 实际`，
而「字段」里**一个都没有**——表单引用了一批不存在的列。
后果：一条合法的「系统」需求写不进下游表，报
`字段「目标」不在建表描述里`。

修法：`TableDescriptionBuilder` 把分类型必填的字段也补成列（可选、归策划端）。

### bug 2：`bridge.apply` 遇到已存在的表整张跳过

于是 schema 加了列也永远到不了下游表，而供给对账那边照样绿——**又一个假绿**。
修法：表在就**补缺的列，只加不改不删**（改类型与删列不可逆，那两件事留给人）。
对用户的真表真跑了一次，补了上面那 6 列。

### bug 3：数组字段写不进文本列

`验收标准` 在 schema 里是数组，下游只有文本列，写方向直接判「不许硬转」。
也就是说**任何带数组字段的需求都推不下去**，而 P8 批次 7b 的往返验证之所以过，
是因为那次的测试记录里根本没有数组字段。

修法：建表描述新增「逻辑类型」键（schema 说这一列原本是什么），
写方向按它序列化（数组一行一条、对象一份 JSON），读方向按同一条规则切回来。
**这不是硬转**——硬转是拿没人定义过的规则去猜，这里规则写在建表描述里，往返闭合且有单测。
