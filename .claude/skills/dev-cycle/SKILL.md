# 开发全流程（高级模型指挥，执行后端干活）

你是大脑，执行后端是手。分工固定，不许调换：

| 阶段 | 谁做 | 为什么 |
|---|---|---|
| 0 铺路 | 你 | 确认执行后端配好，否则派出去必失败 |
| 1 摸底 | 你（大海捞针可派 `explore` 定位） | 要判断这事碰到哪些锁定决策，得有全局上下文 |
| 2 设计审查 | **你，亲自做，不许外派** | 这是整条流程存在的理由 |
| 3 实现 | `implementer` | 方案定死之后是执行题 |
| 4 验证 | `verifier` | 跑命令贴结果，机械活 |
| 杂活（随时） | `operator` | 下载、装依赖的长日志不该进你的上下文 |
| 5 验收 | 你 | 换了个模型在干活，更不能只看它自己怎么说 |
| 6 汇报 | 你 | 说人话 |

## 怎么派

```bash
pwsh Tools/dispatch.ps1 -Role implementer -TaskFile <任务书路径>
pwsh Tools/dispatch.ps1 -Role verifier    -TaskFile <任务书路径>
pwsh Tools/dispatch.ps1 -Role explore     -TaskFile <任务书路径> -MaxRounds 12
pwsh Tools/dispatch.ps1 -Role operator    -TaskFile <任务书路径>
```

执行端走 OpenAI 兼容 API（`local.json` 的「下游配置.oaicompat」+「执行后端密钥」），
带四个工具（读/写/列目录/白名单命令）在本仓库里干活；角色档案在
`Tools/AgentRunner/Roles/`，围栏在 `Tools/AgentRunner/Config/agent-policy.json`。
verifier 与 explore 是**机械只读**的（连 write_file 工具都没有）。

- **任务书先落文件**（放 `_Scratch/tasks/`），命令行只传路径。
- **implementer 用后台跑**（回流常要几分钟）；verifier 通常几十秒，前台就行。
- 回报正文超上限会截头留尾，全文在 `Logs/agent/<时间戳>-<角色>-report.md`；
  逐轮转录在同目录 `.jsonl`。

## 任务书：复制模板填空，不要即兴写

四份模板在 `.claude/skills/dev-cycle/templates/`。复制到 `_Scratch/tasks/` →
逐个 `<>` 填空 → 删掉顶部注释块 → 派出去。**小节顺序和标题不许改**。

### 执行后端看不见你的对话

它是另一个模型，**只能看到任务书里的东西**。所以：

- **设计审查得出的约束和红线逐条抄进任务书**——它们不在任何文档里，不抄它就看不到。
- **已有文档里的背景一律指路，不抄正文**——执行端读得到仓库，写「先读 <路径> 的 X 节」。
- **外部 API 的主机、版本、端点、请求体形状不许凭印象写。** 抄官方文档，并要求执行端
  拿真实回包核对——**第一条要核的就是 base URL**。

## 成本纪律

- **按独立性拆活，不为省调用次数硬合并**；互相耦合的必须合在一起派。
- **过程输出长的活（下载、装依赖、批量转换）派 `operator`**，别自己敲命令吃长日志；
  一条命令几行输出的事自己跑更快。**分界线是输出长度，不是动作类型。**
- **重验收动作按批做**：全量测试、截图这类贵动作每 2~3 个同型单元集中一次。
- **到里程碑就收尾**：写完汇报结束会话，让用户拿检查点结论开新会话续下一段。

## 0. 铺路（每个项目只做一次）

确认 `Tools/CreationPipeline/Config/local.json` 里有「执行后端密钥」与
「下游配置.oaicompat.地址/模型」。不确定就先干跑一次：
`pwsh Tools/dispatch.ps1 -Role explore -TaskFile <任一任务书> -DryRun`。
**任何情况下你都不碰密钥的值。**

## 1. 摸底

读项目指令文件（`AGENTS.md` / `CLAUDE.md`，取第一个存在的）、它点名的文档、
`git status --short --branch`、任务涉及的现有代码。**指令文件和 git 状态必须你自己读。**

大海捞针才派 `explore`；已知改动就在一两个文件里时你直接搜更快。三条边界：
它的返回是线索不是证据，**清单上的文件你自己读原文**；它说「没有别的相关文件」不算数；
它给的任何方案倾向一律忽略。

## 2. 设计审查（你亲自做）

产出六项，写进回复：真正要解决的问题、影响面、红线检查（项目指令文件逐条过）、
方案 + 至少一个被否的替代、验证矩阵、任务拆分（按独立性拆）。
**红线冲突时停下来问用户，这是唯一允许中断的地方。**

## 3. 实现（派 implementer）

任务书填好派出去。回流后先看「工作区=变了/没变」与打断原因，再读回报。

## 4. 验证（派 verifier）

把改动范围写进任务书，让它按范围决定跑哪些门禁。
**命令输出里「工作区=变了」→ 这一轮验证作废**（只读角色动了工作区），重跑。
implementer 自己跑过的自查不算验证。

## 5. 验收（你）

- **无条件自己复跑一条**最能说明本次改动的快门禁——会编证据的模型编出来的东西
  看着就是不可疑的，这条防的正是那个。
- verifier 表格「关键输出行」有没有命令真实打出来的字？没有的当没跑。
- 验证矩阵覆盖了吗？UNAVAILABLE 写清原因了吗？没写清就是 FAIL。
- `git diff --stat` 扫超纲改动；implementer 回报第 4 节（改了既有测试吗）逐条看过。
- **改动新建或收尾了一个模块（编辑器、工具、玩法系统）时，验「模块完成三件套」**：
  模块根 README.md（≤40 行：职责 / 公开面 / 依赖）、`Specifications/Business/<模块>/`
  （有业务规范才建）、`.claude/skills/<模块>/SKILL.md`（这个模块怎么用、扩展点在哪、
  触发词写清——做完编辑器就长出配套技能，别让下一个人从代码里猜）。三件套不齐不算收尾。
- 有 FAIL → 写一份**只讲具体缺口**的新任务书打回。**最多 3 轮**，不绿就停下来告诉用户。

全绿后再提交，提交信息按项目习惯。当前在主分支就先开分支。

## 6. 汇报

四块大白话：做了什么（从用户角度）、验证结果、怎么用、需要他知道的。最后固定一行：

```
派活账：派活 N 次（implementer A / verifier B / explore C / operator D），一次过 M 次，打回 K 次（写崩 X / 任务没写清 Y / 环境不符 Z）。
```

打回原因必须分类：写崩了 → 换模型或改任务书；任务没写清 → 回去改任务书；
环境不符 → 补进任务书「环境」节。**这一行不许省。**
