# 创作管线 · P2 批次 5「审查与放行」日志

> 总账在 [创作管线进度](../creation-pipeline-progress.md)。本文只装这一批的落地记录与验收证据。

## 这一批真正做的是什么

把「这次合并要不要人审」从拍脑袋变成数据驱动的判定，**并且给它加一道数据推翻不了的底线**。

子文档 03「放行模式」那一节有两句看着不冲突、其实要分开实现的话：

> 策略数据 `规范/项目/放行策略.json`，键 = 风险级 × 范围……业务级可就近覆盖
> **基线底线（不可覆盖）**：高危路径与骨架变更**永不自动放行**

前一句说策略可覆盖，后一句说有些东西怎么覆盖都不行。**这两件事必须由两套机制守**——
只靠数据里的「可覆盖」清单守不住，因为清单本身也是数据，改得动。
所以高危范围那条**写进 `ReleaseDecider` 的代码里**，先于策略查询判，
数据里怎么写都推不翻。

## 「收紧 / 放宽」为什么不能套决策 27

决策 27 给资产规格定的规则是「数字变小算收紧、布尔 `false→true` 算收紧、
**字符串等其余一律算放宽**」。放行策略的值是两个字符串枚举 `自动放行` / `人审`，
照那条规则会把 `自动放行 → 人审` 也判成放宽——**那明明是收紧，判反了**。

决策 27 的第三条本来是刻意误伤（一般字符串说不清松紧，判紧会开出「PNG 改 JPG
也叫收紧」那种口子）。但放行值只有两个、松紧有明确定义，那个口子不存在。
所以放行策略用它自己的两值偏序，写在 `ReleasePolicyCatalog` 里，
`AssetSpecCatalog.cs` **一个字没改**（已用 `git diff --stat` 验过零输出）。

| 上层值 → 下层值 | 判定 |
|---|---|
| `自动放行` → `人审` | **收紧**，任意层随便改 |
| `人审` → `自动放行` | **放宽**，只有基线把该键列进 `可覆盖` 才允许 |
| 第三种值 | 非法，报一条发现并沿用上层值 |

38. **高危范围永不自动放行这条写在 `ReleaseDecider` 的代码里，先于策略查询判。**
    数据里的「可覆盖」清单本身也是数据、改得动，守不住底线。

    一次报全部原因，比来回跑三趟有用。

## 执行后端这一轮报上来的四件事（都属实，两件是我任务书写松了）

1. **`TaskReleaseArguments` 没法继承 `TaskRiskArguments`——这是我任务书写松了。**
   任务书写「在 TaskRiskArguments 那几个之上再加 AllGatesGreen」，但那个类是 `sealed`，
   首跑 build 报 CS0509。它改成平铺复制全部属性，与文件里其他参数类风格一致。行为无差异。

   标了「序数序」，它给 `HighRiskScopes` 也排了，结果测试期望 `[框架, 引擎]`、
   实际得到 `[引擎, 框架]`（序数序下「引」在「框」前）。改成不重排后转绿。
   **这是本批唯一一次真实的红→绿**，它如实说了其余 28 个测试是一次通过的。
3. **`ReviewPackageBuilder` 的高危范围是硬编码兜底**，因为 `Build` 的签名里没有 catalog。
   这是我任务书没指定。**记进已知缺口**，不算错。
