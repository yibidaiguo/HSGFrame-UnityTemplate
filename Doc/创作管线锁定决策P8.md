# 创作管线 · 锁定的设计决策（P8 起）

> 从 [创作管线锁定决策](创作管线锁定决策.md) 续号。那份写到 179 行，离 200 行硬顶不够放新条目。
> **改这里的任何一条都要重新走设计审查。** 决策 1–79 在上一份。

80. **执行后端 driver 按协议命名，不按厂商命名：`oaicompat`。**
    子文档 05 §八原本写的是 `claude`。不能用，理由是**门禁**：
    下游边界门禁把全部 driver 名当禁止串，逐行扫 `Tools/{CreationPipeline,Cli,Dashboard}`
    下的 `*.cs`，而 `claude` 这个词已经出现在那片代码的注释与文案里——
    选它等于当场点着门禁，而决策 17 说这道门禁不许加豁免。
    按协议命名还有个附带好处：DeepSeek / 通义 / 智谱 / 自建 vLLM 谁的 key 都能接，
    换厂商不改 driver 名、不动门禁。
    **推论：以后新增 driver 先拿名字去 `Tools/` 那三棵树里 grep 一遍，撞了就换名字，
    不要去加豁免。**

81. **daemon 是循环外壳，必须支持「跑满 N 轮自己退出」；无限循环是 `最大轮数=0` 的特例。**
    决策 54 当初写「不写常驻 daemon」，理由是「常驻进程在门禁里没法验」。
    有限轮把这条前提解掉了：门禁跑 3 轮、假时钟、假 sleep，判定链路全程可复现。
    决策 54 的另一半仍然成立且不许动——**外壳不做判定**：
    daemon 只干「取活判定 + 记账 + 消费唤醒」三件事，
    取到活之后真去执行工作项是别的命令的事（决策 52 同源）。

82. **唤醒事件源先落「文件投递」这一种，飞书事件订阅是另一条路。**
    `_Tasks/唤醒/*.json` 出现即算一次唤醒信号，处理后**移动**到 `_Tasks/唤醒/已处理/`，
    不删（决策 7：留证据，靠幂等挡重复）。
    这不是桩——它是一条真能跑通的唤醒通道，且不假装自己是飞书。
    飞书那条要么长连接、要么内网穿透，两条都要真租户，归 P8-7/P8-8。
    **信号必须在判定跑完之后才消费**：判定崩了信号要留着，
    否则信号丢了而账上什么都没有（决策 63 同源：先证据后状态）。

83. **一轮崩掉不许让 daemon 死掉，但也不许静默。**
    判定抛异常那一轮产一条 `判定跑成=false` 的记录、原因写异常消息，然后继续下一轮。
    `判定跑成=false` 与「这一轮没取到活」是两支，不许合并——
    合并会把崩掉的判定印成「队列里没活」（决策 42 的 daemon 版）。

84. **driver 实现落 `Bridges/<名>/src/`，不落 `Tools/`。**
    下游边界门禁的扫描根写死是 `Tools/{CreationPipeline,Cli,Dashboard}`；
    实现里必然要出现自己的 driver 名，落在 `Tools/` 下必红。
    `Bridges/` 是那道门禁的白名单（子文档 05 §六），且目录名全 ASCII，
    满足决策 1 的「含 .cs 的目录必须 ASCII」。
    **新工程必须加进 `Solutions/Template.sln`**，否则十秒级门禁编不到它，绿灯是假绿。

85. **driver 可执行的解析走 `Config/创作管线/下游.json` 的实现表，
    既不写进 `driver.json`，也不靠约定路径推导。**
    `driver.json` 是进 git 的共享契约，不该带本机路径；
    而按 `bin/<配置>/<框架>/` 推导会在 Debug/Release 切换、目标框架升版时静默失效——
    静默失效的表现是「找不到实现」被当成「下游没配」，那是决策 42 那类假象。
    实现表的值是**仓库相对路径**（bridge 是仓库内 build 出来的，跨机一致）；
    机器特有的东西（ComfyUI 地址、Blender 可执行文件、密钥）全在 `本机.json`。

86. **`本机.json` 不许预生成空值键。** 面板判密钥配没配只看键在不在（决策 78），
    预填 `"飞书应用密钥": ""` 会让面板显示「已配」，那是假绿。
    模板文件另起名 `Config/创作管线/本机.示例.json`，**填不了的键要求整条删掉**。

87. **配方的 `workflow.json` 保持中文骨架格式，加一个 `连线` 键，
    不换成 ComfyUI 原生 API 格式。**
    骨架至今只有 `类型` + `参数`，没有任何连线信息，所以翻译不出一张能跑的图。
    两条路：换成 ComfyUI 原生的 `class_type` / `inputs`，或者给骨架补 `连线`。
    **选后者**，理由是解耦：`映射.json` 的「节点id + 参数名」这套间接层，
    本来就是为了让配方不绑死在某一个下游上（决策 11 同源——
    字段类型映射住 driver.json 不住 C#）。换成原生格式，
    以后换一个生图 driver 就要把全部配方重写一遍。
    `连线` 的形状是 `{"参数名": ["上游节点id", 输出下标]}`，
    桥在调用时把 `类型`/`参数`/`连线` 翻成下游认识的形状。
    **这是向后兼容的改动**：`RecipeInspector` 只查「映射点到的节点 id 在不在
    workflow 的节点里」，不校验节点对象的内部形状，所以 `gate.recipe`
    与 `映射.json` 一个字都不用动（核实过）。

88. **能力对账的绿，只在依赖真下完之后才算数。**
    决策 31 定死「只查在不在，不比版本」，而下游列候选的方式通常是**列目录文件名**——
    P8 装机时实测：`sd_xl_base_1.0.safetensors` 才下到 0.14G / 6.9G，
    ComfyUI 的 `/object_info/CheckpointLoaderSimple` 已经把它列进候选，
    `art.caps` 会照报「依赖 2 项，全部满足」，然后真出图时炸在模型损坏上。
    **这个洞决策 31 天生堵不住**（要堵就得比哈希，而没有真跑过的样本定不出基准）。
    所以规矩是**流程上的**：装依赖的那一步没报完成之前，
    不许把 `art.caps` 的绿当验收凭据。
    **推论：`art.caps` 绿 + 真调用失败，第一个要怀疑的是依赖只下了一半，
    不是代码写错了。**

89. **LLM 判定的产物一律是「建议」：不进门禁、不改状态、不写进任何账本的判定字段。**
    门禁的价值全在于可复现——同一份输入两次跑必须同一个结论（决策 58 为此
    连一个随机数都不许用）。LLM 天生做不到这件事，把它接进 `gate.*` 等于
    把「这次红这次绿」写进验收标准。
    所以：AI 对抗预审、语义冲突比对、影响映射评估三样，**产出的都是报告文件**，
    发现分级（阻断级 / 建议级）只是**报告里的字段**，
    要不要因此回去修是人和引擎的决定，不是门禁的判定。
    **`gate.ps1` 里永远不许出现调 LLM 的那一步。**
    报告里必须写清**用的哪个模型、哪一版提示词**——
    不写的话，两个月后没人说得清那条「阻断级」是怎么来的。

90. **LLM 报告按输入哈希缓存，缓存命中不重判（子文档 07 §四）。**
    这不只是省钱：同一份输入拿到同一份结论，是把不可复现的东西
    往可复现方向压的唯一手段。缓存键必须包含**模型名与提示词版本**——
    换了模型还命中旧缓存，报告就在说谎。

91. **线上 driver 的「能不能用」，只有真提交一次任务才算数。
    余额接口、密钥非空、HTTP 200，都不是就绪判据。**
    别拿「没查出问题」当「查过了」（决策 42 的线上版）。
    **线上 driver 的试跑就该是一次真任务**，哪怕最小的那种。

    **这条的由来（含一次判错，留着当教训）：**
    tripo 的 `GET /user/balance` 回 `{"balance":0,"frozen":0}`，
    而账号控制台上显示有 200 免费积分。Claude 当时据此推断
    「免费积分不进那个字段，所以余额接口不可信」——**推断错了**。
    真提交一次任务后拿到的是
    `403 code=2010 "You don't have enough credit to create this task"`：
    **`balance: 0` 一直是准的，控制台那 200 积分不能用于 API 调用。**
    两次都指向同一个结论（余额接口不能当判据），但**理由完全相反**：
    第一次以为它漏报，实际是它没漏报、是控制台那个数与 API 无关。
    **两个数字对不上时，不许挑一个顺眼的去解释另一个——去真跑一次，
    让第三个事实来裁决。**

92. **拿用户免费额度做的验证，次数写进任务书，不许「多试几次看看」。**
    免费积分会过期、会用完，而且花的不是我们的钱。
    验链路通不通，一次就够；要留余量给后面真用的时候。

93. **下游边界门禁有个盲区：它只 grep driver 名，
    所以「不提厂商名的厂商专属知识」能大摇大摆走进引擎层。**
    P8 批次 7 真发生过：飞书多维表格建表接口的数字类型码（文本=1、数字=2、
    单选=3、多选=4、复选框=7）被写进了 `Tools/CreationPipeline/`，
    类名叫 `DownstreamFieldTypeCodec`、注释里一律称「目标平台」——
    **门禁全绿，而边界已经破了**。那几个数出了飞书毫无意义，
    换个需求编辑端就要改引擎，正是决策 11「供给引擎完全泛化」要拦的东西。
    **所以这道边界最终只能靠人看**：审 `Tools/CreationPipeline/` 的新文件时，
    问一句「这段知识换一个下游还成立吗？」不成立就该住进桥里。
    门禁能拦住的只是最蠢的那种越界（直接写 driver 名）。
    已挪到 `Bridges/feishu/src/BridgeFeishu/FeishuFieldTypeCodec.cs`，
    测它的那份测试因此要引桥工程。


94. **外部 API 的主机、版本、端点与请求体形状，一律以真回包为准，
    不许照文档抄、更不许凭印象写进任务书。**
    待办 3 那笔债的根因就是这个：`本机.示例.json` 里那个 v2 的 base URL 是凭印象写的，
    执行端照着任务书建了整座桥，编译测试门禁全绿，而打的是已作废的一套接口。
    **可操作的做法是「用错误码给端点画地图」**——线上服务通常把三种拒绝分得很干净：
    「端点不存在」「参数非法」「余额不足」。所以**账号没钱照样能核准形状**：
    发一次请求，回的是「余额不足」就说明 URL 与形状全对，回「参数非法」就说明形状不对，
    回「端点不存在」就说明 URL 不对。tripo 上这三个码分别是 4001 / 1004 / 2010。
    **推论一**：错误码映射要按**服务端 code** 判分支，不许只按 HTTP 状态码——
    同一个 404 底下「任务不存在」与「端点不存在」是两件事，混在一起会把
    「base URL 写错了」印成「任务没找到」，这正是这笔债能潜伏那么久的原因。
    **推论二**：官方文档也会写错（tripo 快速开始页上的 `tripo-v3.1` 服务端当场拒），
    服务端自己列出来的允许值才是真的。
    **推论三**：没被真回包核过的那部分要在代码注释里写明「未实证」，
    并且第一次跑通时必须回来收敛。
