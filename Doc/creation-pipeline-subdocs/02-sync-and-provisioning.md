# 同步与供给(创作管线子文档 02)

> 上游:总方案 §四。两个方向:把内容收回来(同步),把编辑器铺出去(供给)。

## 一、字段所有权

- 内容字段(标题/描述/验收标准/分类型必填/业务字段):策划端所有,`锁定=true` 后冻结;
- 状态/来源/关联/同步/冲突:工程所有,下游只读;
- 专项的**认领字段**:下游成员编辑所有,工程只读同步进来;专项其余字段归策划端。
- 同步永远单向复制。所有权之外的改动:入站被拦截(锁定后进变更通道),出站直接覆盖下游。

## 二、入站(pool.pull)

1. 取记录:唤醒模式事件携带记录 id;轮询按「最后修改时间 > 水位」拉增量,水位存 `Config/sync-watermark.json`。
2. 幂等:Inbox 文件名含记录修订号,同名即跳过。
3. 校验:合并 schema + 分类型必填 + 枚举。失败 → 用错误文案回贴(需求编辑端 port 的 comment 命令),记录留 Inbox,状态不动;策划改动触发新修订,自动重走。
4. 冲突扫描:对设计池汇总与存量需求做比对(执行后端跑,输出冲突候选 + 置信度;低置信度只在需求上标注,不发卡)。确认冲突 → 三选一卡片,按选择处理(总方案 §三)。
5. 入池:写 `Requirements/REQ-xxxx.json`,自动 commit `[入库] REQ-0042 七日签到`,同步字段回写下游。

已锁定记录的下游改动:不入池,落 `_Tasks/REQ-xxxx/变更/<时间戳>.json`(字段级 diff,多次变更合并为最新累积 diff;任务尚未开跑则先建壳目录),触发引擎暂停信号;下游回贴「已锁定,改动已转为变更请求」。

## 三、出站(pool.push)

- 触发点:状态变化(待验收/已完成)、拒收、冲突发起、任务停等喊人。
- 动作:回写状态字段 → 按事件发卡片(消息卡片 port,模板:选片/关卡/冲突/完成/喊人)。
- 完成卡片附验收报告摘要 + 截图(图片经消息卡片 port 上传)。

## 四、供给(bridge.provision)

命令:`bridge.provision --driver feishu [--dry-run]`
输入:合并 schema + 设计池汇总 + 术语表 + 历史正反例(被验收/被打回的真实需求,人工标注)。

产物(`_Generated/Bridges/feishu/`):

1. **table-description.json**:字段清单(名称/bitable 类型/单选项/必填)+ 分类型三张表单定义。首次建表直接执行;表已存在则输出差异脚本——加列/加选项自动做,**删列只列出来等人确认**。
2. **assistant-package/**:
   - `system-prompt.md`(角色、schema 摘要、填写指南、冲突提醒职责)
   - `知识/design-digest.md`、`知识/glossary.md`、`知识/examples.md`、`知识/modules.md`
   - `import-guide.md`(Aily 手工导入步骤)
   - `fingerprint.json`:{schema_hash, 设计池汇总_hash, 生成时间}
3. **validation-messages.json**:规则 id → 人话提示;pool.pull 拒收与助手提示共用,不会两张皮。
4. **专项表**:专项铺成 bitable(一行一专项,每职责一个人员多选「认领」列);认领改动经既有 pull 通道拉回专项文件——**认领零新接口**,后接其他下游软件同理。

对账门禁:重算两个 hash 与指纹比,不一致红 → 提示重跑 provision(+重新导入助手)。

## 五、助手两形态

- **A(v1,Aily 配置包)**:spike 验证点——能否 API 建/更新 agent 与知识;不能则人工导入,provision 只负责产包与提醒过期。
- **B(v2,自托管)**:常驻进程 `assistant-serve`,经 lark-event 订 IM 消息 → 带上这条会话的历史问执行后端 → 现场跑 `req.validate` → **回一张确认卡,人点「一键建需求」才写 bitable 草稿**。与 A 共享全部知识文件。

B 形态的三条形状(改任一条要重走审查):

1. **面向策划、美术、程序三种人**。谁来都先把要干的事聊明白再谈落表;要图的人若没有对得上的既有需求,先把这件事聊成一条需求,再谈画什么。助手一轮最多问两条,且问人话不问字段名——把 schema 摆到人脸上,人看到的就是一张表而不是一次对话。
2. **会话带上下文**。历史落 `_Tasks/conversations/history/<会话>.jsonl`,只追加;「开新话题」往里插一条分隔线,读取只取分隔线之后——**上下文丢了而账本还在**。按钮之外也认打字说「开新话题」,免得这条出口依赖单一通道。
3. **建不建由人点**。校验通过只产出待确认草稿(留底在 `_Tasks/conversations/drafts/`)与一张带按钮的卡;人点了才动手,并记进 `_Tasks/conversations/confirmed.jsonl` 防重复点。点完一路做完四步,否则「一键」是假的:**写需求池** → 投唤醒信号 → `doc.render` 出 index.md 再 `doc.push` 推成知识库「需求」节点下的一份文档 → **任务表加一行**并挂上文档链接。写池子是直接写、不绕下游——需求在下游只是一份给人看的文档、不回流,池子才是唯一事实源。任务与需求的连线用超链接列而不是飞书关联列:关联列只能关联同一个多维表格里的记录,文档关联不过去。**不派活**——执行人、进展、日期几列一律留空,那是 PM 的决定。回话按三段如实说(池子成了、文档推没推上、任务行加没加上),不许一句「建好了」盖过去,更不许写成「已交给引擎排活」(确认与排活至今没有命令能做,`queue.json` 没有写入方)。按钮回调经旁路订 `card.action.trigger`,归一成同一个「会话」块投进同一条队列——引擎侧不认识飞书卡片(决策 93)。

4. **人发的图片与文件也是话**。归一那一步把每条消息抠成「文本 + 附件」,不管它在下游叫 text 还是 post 还是 file;判「这条能不能处理」看的是**有没有正文或附件**,不是「类型是不是 text」——人甩一张参考图配一句「照这个再出一张」,那句话已经说完了,回一句「我只认文字消息」是把话扔了。附件由桥取回本地(`fetch` 动作,归一那一步只留 key,下载属于下游知识),落在 `_Tasks/conversations/attachments/<会话>/`;**必须落成文件**,因为下游的资源 key 是按消息取的,过一会儿人点「出图」时那条消息早处理完了。图片一并喂给执行后端看,别的文件在提示词里以文字交代。带了参考图时**参考图路径钉进出图请求本身、赶在算请求 key 之前**:key 是请求内容的哈希,换一张参考图就该是另一个请求,事后再塞会让两次不同的参考图撞成同一个 key,第二次被幂等挡掉。出图配方按「有没有参考图」分两份(见 `Config/asset-recipe.json` 的「文生图」/「图生图」),**查不到图生图那份就如实报,不退回文生图**——退回去参考图会被悄悄丢掉,图照出、钱照花,跟人给的那张却没关系。

5. **拆图 = 逐个重绘,不是裁一刀**。先出一张整屏预览定方向,定了才点「拆图」:视觉模型标框 → 每个框裁出一小块**当参考图** → 走图生图配方 `ui-element@v1` 让模型只把这一个元素重画成透明底单图 → 落 `Art/Texture/Ui/` → 写 `UI/Definitions/<面板>.uidef.json` → **当场跑 `ui.scaffold`** 出 UXML/USS/C#。
   为什么不直接用裁下来的那块:元素互相压叠时一刀必然带上邻居;白底上的白件抠底会顺着主体一路灌进去打洞(真炸过——拆出来的立绘白衣白发全是破碎的挖空)。这两条本地都解不了,透明底与元素独立得让模型重画才有。代价是**每个元素一次生图调用**,一屏十几个元素要跑几分钟,所以按钮点下去要立刻撤掉、卡上报进度(标到几个、正在重绘第几个),失败才把按钮换回来。
   裁出来的参考片段落 `_Tasks/cut-pieces/`,**不进正式落点**——它带着邻居与底色,是给模型看的,不是成品。
   写了 uidef 就必须生成三件套:生成物幂等门禁扫 `UI/Definitions/` 下每一份定义,只写定义不生成产物,下次跑门禁必红,而红的原因跟拆图看着毫无关系。
6. **透明底只管 UI 元素,不管底图**。父配方 `ui-base@v1` 里放的是 UI 这类**共有**的约束(不出文字、元素边界不压叠);「透明背景」住在 `ui-element@v1`。界面底图是整屏最底下那一层,本来就该铺满不镂空——焊在父配方里的话这两类需求当场打架(底图被要求透明,归一那步每次都报「四角不同色,没敢抠透明」,那句话对底图毫无意义)。

## 五之二、下游对象台账

链路要用的下游对象(知识空间 / 多维表格 / 任务表 / 策划文档父节点)统一走一条规矩:**台账里有就验它还在不在、在就用;没有或验不过就建;建完 id 回填台账**(`bridge.ensure`)。

- **台账 `Config/downstream-objects.json` 进 git**,只放非密钥的对象 id;密钥仍旧只在 `local.json`。对象 id 放进不进 git 的地方,换台机器就会重建一批,同一个项目在下游有两套表。
- **自己建出来的对象,应用就是所有者**,不会再撞「建表 403 / 建节点 131006」。
- **「没权限」不许当成「不存在」**:前者停下来让人授权,后者才重建;合并的话每跑一次就在人家知识库里多建一个空壳。
- **知识空间那一样飞书只认用户身份**(`POST wiki/v2/spaces` 用应用身份回 `Invalid access token`),必须人手工建一次并把应用加进**空间成员**(不是文档协作者)给编辑权。其余三样空间到位后全自动。

## 六、schema 升版

- schema 带 semver;升版时 provision 附迁移说明,存量需求记录打版本标。
- 破坏性变更(删字段/改枚举语义)升 major,必须附迁移脚本;门禁「扩展合法性」拦项目层的破坏性改动。
