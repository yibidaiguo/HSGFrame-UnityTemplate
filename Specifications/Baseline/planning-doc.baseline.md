# 模块策划案规范 · 基线

一个模块在设计池里是一个目录（`Pools/Designs/Modules/Inventory/`），
目录里的 `index.md` 就是这份规范管的东西：**这个模块的策划正本**——
它为什么存在、玩法是什么、代码现在什么样、往后要做成什么样。

它与[需求文档](requirement-doc.baseline.md)分工不同，两层缺一不可：

| | 需求案 `REQ-xxxx` | 模块策划案 |
|---|---|---|
| 粒度 · 数量 | 一件要做的事 · 很多 | 一个模块 · 模块数量级 |
| 用途 | 派活、进任务表、验收 | 统合：有过哪些需求、代码现状、未来实现 |
| 生命周期 | 做完归档 | 常驻，随需求验收更新 |

**为什么非要有这一层**：需求案做完就归档，而「这个模块现在统共是什么样」
是个随时要回答的问题。没有这一层，答案散在几十条已归档的需求里，谁也拼不回来——
新人问「背包能干什么」只能去读代码；策划要加一条需求，无从知道会跟哪条旧需求打架。

规范分两层：**这份基线由模板发**，项目层可以在
`Specifications/Project/planning-doc.json` 里**追加**小节与 frontmatter 键，
**删不掉基线定的任何一条**——那个文件的形状只表达得出「加」，表达不出「删」。

## 二、四条硬规矩

1. **一个模块一份。** 模块名就是 `Scripts/Modules/` 底下那个目录名，
   ASCII、PascalCase（决策 1）。跨模块的通用功能可以单列一份，
   但那时它自己就是一个「模块」——不许一份策划案讲两个模块。
2. **人写区与生成区分开，中间没有第三种。** 目标用途 / 玩法 / 边界与不做 /
   往后要做成什么样是人写的；现状是机器写的。人不许手改生成区（`生成区hash` 查得出来），
   机器也不许碰人写区——**这条是这份文档能长期活下去的全部原因**。
3. **生成区是投影，不是正本。** 需求正本在 `Pools/Requirements/`，界面正本在
   `Pools/Designs/Interfaces/`，配置表正本是 `Config/Schema/`，代码正本就是代码。
   现状那一段是它们的投影，随时可以整段重算。要改内容去改正本，不是改这里。
4. **需求验收之后必须重渲染。** 一条需求走到「已完成」，它所属模块的策划案就过期了。
   过期的正本比没有正本更糟——人会照着它做决定。所以这一步是自动的，不靠人记得。

## 三、必填与选填

```json
{
  "版本": "1.0.0",
  "frontmatter必备键": ["模块", "标题", "状态", "文档版本", "权威侧"],
  "状态取值": ["生效", "已废弃"],
  "权威侧取值": ["飞书", "项目"],
  "必填小节": ["目标用途", "玩法", "边界与不做", "往后要做成什么样"],
  "选填小节": ["事件往来", "存档", "已知问题", "参考媒体"],
  "生成区小节": "现状",
  "生成区子节": ["需求", "界面与交互", "配置表结构", "参考图", "代码公开面"],
  "生成区标记开始": "<!-- 生成区开始：勿手改，plan.render 重生成 -->",
  "生成区标记结束": "<!-- 生成区结束 -->"
}
```

三处判断：

- **「往后要做成什么样」是必填不是选填。** 一份只写现状的文档，读的人无法判断
  某个缺口是**还没做**还是**故意不做**——而这两件事对要不要提需求的影响完全相反。
  「边界与不做」管后者，这一节管前者。
- **「配置表」在 frontmatter 里由人声明，机器不猜。** `Bag` 这张表归 `Inventory`
  没有任何字面依据可推（名字都对不上），靠猜迟早把 Monster 表算进背包。
  声明了机器就照 `Config/Schema/<表>.schema.json` 渲结构，人不必手抄字段——
  **手抄的那份一定会与表漂**。
- **生成区子节固定五节，缺料就写「暂无」**，不是省略。省略读起来像「还没轮到」，
  而「暂无」说的是「查过了，确实没有」——那是两件事（决策 42 那一类）。

## 四、界面规格怎么回写进来

一屏界面的元素行为表与白块布局图，正本在 `Pools/Designs/Interfaces/UI-xxxx.json`，
**投影落在这份文档的生成区**（`### 界面与交互`）与 `media/`。

**为什么是模块层不是需求层**：界面是模块的属性——需求做完就归档，而这一屏还在。
铺在需求案里的结果是同一个面板被 N 条需求各存一份快照，谁是正本说不清；
人真要查「这一屏现在长什么样」时，翻到的多半是某条半年前已归档需求里的旧版本。
需求案那边只留一行指针：`界面规格：UI-0001「背包」（元素 7 个）→ 详见模块策划案 Inventory`。

归属认的是规格里的 `模块`（缺省退回 `面板`）：**一个模块可以有好几屏**
（背包主界面 + 背包设置弹窗），那时面板名各不相同而模块是同一个。

布局图**必须真拷进 `media/`** 才在文档里引它。不引 `_Generated/`：
那是本机产物、进 .gitignore，换台机器 clone 下来图就断了，
而这份文档是要推给别人看的。引一个不存在的路径在飞书上是一个碎图标，比不放更难查。

重渲时机两个，都是自动的：出完功能图那一刻，以及每条需求验收
（`pool.push --EventName 已完成`）之后。

## 五、推知识库

`plan.push` 把它推成一个知识库节点，挂在台账的**模块策划案父节点**下面——
不是需求文档那个。两层混在同一个父节点下，几十条做完就归档的需求会把
十来份常驻的模块正本淹掉，而人往知识库里找的，九成是模块正本那一份。

**只推变了的**：正文哈希与「同步.最后同步hash」一致就跳过。这份文档每条需求验收都重渲一遍，
而重渲九成时候没变化——不比对就等于每验收一条需求都往知识库写一次全量，
白花调用还把节点的修改历史刷满，而人翻修改历史正是为了看「这次到底改了什么」。

同步账写在 frontmatter 里，**不进正文哈希**：算进去的话每推一次都会改哈希，
下次又判定「变了、要再推」，一份文档会自己把自己推到天荒地老。

推上去了但同步账写不回来时如实报「下次会重推」，不谎称成功——
谎称的后果是节点在、账没记，下次跳过，而人以为看的是最新的。

## 六、参考图从哪来

`Pools/Designs/Art/<模块>/refs/` 里那些**效果图**（人点确认时带进库的那张原稿），
加上该模块生效的风格定稿与色板。这一段不必人维护：选片即入库那条链已经通了
（子文档 10 §四），策划案只是把库里已有的按模块列出来。

## 七、冷启动

一个模块第一次建策划案时，草案由 AI 合成、人审：
读该模块的代码摘要（公开类型与成员）、`README.md`、以及池子里挂在它名下的需求，
拼出「目标用途 / 玩法 / 现状」的初稿，`往后要做成什么样` 留空等人写。

**AI 不许编「往后要做成什么样」**——那是人的判断，代码里没有依据。
编出来的会被往后所有东西当成事实继承（与总设计层同一条规矩，子文档 10 §四）。

## 八、门禁挂钩

| 门禁 | 查什么 |
|---|---|
| 必备键与必填小节 | frontmatter 五个键、四个人写小节都在 |
| 生成区未被手改 | 正文算出来的哈希与 `生成区hash` 对得上 |
| 模块名合法 | 与 `Scripts/Modules/` 下的目录名对得上，或显式标为跨模块通用件 |
| 配置表声明可解析 | `配置表` 里每张表都能在 `Config/Schema/` 找到 schema |
| 媒体引用可解析 | frontmatter `媒体` 里每条路径都真在 `media/` 下 |
| 不空转 | 「往后要做成什么样」不许只有占位符——那等于这一节没写 |

## 九、还没定的

- **事件往来与存档**先做成选填人写小节。两者都能从代码里推
  （`Events/` 下的类型、Save 模块的存档块），但推得准不准没验过，
  推错的事实比没有更糟——先让人写，等推法验稳了再挪进生成区。
- **跨模块通用件怎么标**：`模块` 那一格填什么、门禁怎么放行，没定。
  倾向加一个 `跨模块: true`，但等真有第一份再定，别先铺格式。
- **一个模块两块屏**时界面那一节怎么排序：现在按界面 id，没验过读起来顺不顺。
