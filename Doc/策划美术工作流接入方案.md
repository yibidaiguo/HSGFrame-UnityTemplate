# 创作管线:策划与美术工作流接入方案

> 状态:草案 v1 · 2026-08-18
> 定位:HSGFrame-UnityTemplate 的下一层——把「纯程序工作流」扩成「策划定需求、美术定风格、工程自动执行、人随时可插手」的闭环。全套机制统称**创作管线**。
> 落点:本方案放仓库根 `Doc/`;定稿后规则条目拆进 `规范/`,机器拆进 `Tools/`。
> 模板/项目边界:模板仓库只装机器(引擎、检查器、基线规范、面板),零池子内容、零资产、零飞书配置;`project.create` 生成项目时铺空池子。第一宿主为专用测试小项目。

## 〇、六条铁律(叠加在模板五条之上)

1. **池子是唯一事实源,下游皆视图。** 需求池/设计池以文件住在仓库;飞书、腾讯文档、生图工具都是它的编辑器或渲染结果。
2. **阶段产物皆可 diff 文件。** 每个执行阶段的输入输出必须落盘、必须能被 git diff 看见——人工干预的全部能力由这一条买来。
3. **人改即权威。** 人编辑过的中间产物视为定论,下游从它续跑;上游重新生成不得静默覆盖人的修改。
4. **引擎与骨架写死,规则数据分层。** 检查器与管线引擎随模板升级;规则数据分基线(模板发)/ 项目(全局,自由改)/ 业务(只管该业务,就近覆盖)三层。
5. **校验在收口,不信任下游。** 助手再聪明,入池仍须过 schema 校验;拒收带字段级理由回贴。
6. **人审即门禁。** 审美、方案、合并这些人的判断,建模成与机器门禁同构的关卡,可配置在哪停。

## 一、总体结构

```
策划端(飞书 bitable + 助手)        美术端(选片卡片 / 概念定稿)
        │ 入库:常开、无人值守、自动 commit        │
        ▼                                        ▼
   Bridges/(driver 适配层) ───────► Pools/(仓库 = 唯一事实源)
                                        │ 状态→已确认(白名单确认人)
                                        ▼
                              执行引擎(任务 = 目录 + git 分支)
                              阶段产物皆文件,人随时接管
                                        │ PR 终审(默认人审;低风险业务可配放行)
                                        ▼
                              回同步:状态 + 摘要卡片 + 截图
```

目录布局:

```
Pools/
  Schema/              ← 需求/设计记录/工作项/资产请求的 schema(基线+项目两层)
  Inbox/               ← 下游推入的原始内容,未验证不入正式引用
  Requirements/        ← 需求池:一需求一文件
  专项/                ← 范围层:EP-xxxx.json(含认领)
  组织/                ← 成员.json(默认职责+确认权)、卡片路由.json
  审查意见/            ← 终审打回意见库(只追加,喂预审与晋升)
  队列.json            ← 已确认待执行队列
  Designs/
    记录/              ← 只追加的设计记录(账本)
    汇总/              ← 工具生成的每模块「当前设计」(余额,生成物不手改)
    定稿/              ← 风格定稿:色板/形状语言/参考/负面清单,带版本
    冲突列表.json      ← 未裁决的设计冲突债务
Bridges/               ← 下游适配器,一夹一个 driver(feishu/ comfyui/ blender/ …)
Config/                ← 环境层:下游.json / 本机.json(密钥)/ 引擎.json / 同步水位
_Tasks/                ← 任务工作区(阶段产物)
_Generated/Bridges/    ← provision 产物(建表描述/助手配置包/错误文案)
```

### 数据分层(八层,职责分明不乱串)

| 层 | 内容 | 落点 | 写入者 | 进 git |
|---|---|---|---|---|
| 产品层 | 游戏代码/资产/配置/场景 | `UnityProject/` | 任务执行,经 PR | ✓ |
| 机器层 | 框架包/工具链/检查器/面板/Bridges | `Packages/` `Tools/` | 程序,随模板升级 | ✓ |
| 规则层 | 规范三级/方向/提案 | `规范/` | 管理员 + 晋升流程 | ✓ |
| 协作层 | 需求池/设计池/专项(含认领)/冲突/队列/成员与路由/审查意见 | `Pools/` | 同步器/引擎/面板,按字段所有权 | ✓ |
| 过程层 | 任务工作区/关卡意见/变更 | `_Tasks/` | 引擎 + 接管的人 | 完成后归档 |
| 环境层 | driver 配置/密钥/引擎模式/水位 | `Config/` | 管理员;密钥每机自配 | 共享✓ 密钥✗ |
| 生成层 | 生效规范/供给产物/门禁报告 | `_Generated/` | 工具,幂等 | ✓(对账) |
| 暂存层 | 变体缓存/探索出图 | 缓存目录 | driver | ✗(溯源进) |

**归属总则:产品数据跟随项目,协作数据的结构与机器跟随框架**——协作层的目录布局/schema/状态机是模板资产(基线锁定,项目仅经扩展点加字段),`template.upgrade` 改协作结构时附带存量数据迁移;协作数据的**内容实例**仍在各项目仓库。产品层内容框架永不定义,只经门禁与管线触碰。

三条纪律:① **产品层零协作感知**——删掉 `Pools/` `_Tasks/` `规范/` 游戏照样编译运行,协作数据永不进 `UnityProject/Assets`(「层边界」门禁查);② **写入者唯一**——每类数据一个写入方(或按字段所有权切),同一文件不许两套系统写;③ **事实与再生分离**——生成层/暂存层随时可删重来,备份对象只有协作层与产品层。

## 二、需求模型:两层

### 需求层(策划的语言)

骨架字段(模板写死,机器契约):
`id / 类型 / 状态 / 来源 / 验收标准 / 关联设计记录 / 父需求 / 依赖 / 专项(可空) / schema版本`

业务字段(项目层自由加):优先级、模块归属、排期、平台标记……对机器是**不透明数据**,直通渲染(bitable 列、助手知识)与同步,引擎零依赖。

类型:基础三种,项目可扩展(加类型 = 加一条「类型→管线模板」映射数据,不改引擎):

| 类型 | 必填 | 管线 | 设计池义务 |
|---|---|---|---|
| 系统 | 目标/玩法/验收标准 | 方案(含拆解)[人审] → 工作项 → 集成验收 | 必须产设计记录 |
| 修改 | 改什么/现状/期望 | 影响评估 → 执行 → 验收 | 动了既定设计才记变更 |
| 缺陷 | 复现步骤/期望/实际 | 复现(先落成失败测试) → 修复 → 回归 | 不动;查出属设计问题转「修改」 |

状态机:`草稿 → 已确认 → 进行中 → 待验收 → 已完成`,任意状态可 → `已作废`。
「待验收」= 策划验收效果(是不是我要的),与技术终审(PR)双线并行,见 §五阶段细则。
同步不是状态,是字段(最后同步哈希/时间)。
**「已确认」是自动执行的扳机,只有白名单确认人可拨**(见 §十一)。

### 工作项层(工程的语言)

方案/评估阶段由 AI 把需求拆成工作项,人审关卡顺带审拆解。策划不写工作项。

字段:`id / 需求id / 域 / 状态 / 依赖 / 产物`
域:`代码 / 配置 / 资产.生图 / 资产.模型 / 资产.动画 / 文档 / …`

- 每个域绑自己的子管线与门禁:代码域走编译测试门禁,资产域走规格机检 + 选片人审。
- 项与项有依赖(图标先出、UI 代码后接);依赖图同时服务「变更标脏」(§四)。
- **需求完成 = 全部工作项完成 + 集成门禁绿 + 设计池义务履行**(门禁查)。
- 美术端看到的「资产请求队列」= 域=资产.* 的工作项视图,天然衔接选片与风格锚点。
- 修改需求的影响评估兼**分流阀**:评出一两个工作项直接跑;涉及面超阈值升级为带人审的完整方案关。

## 三、设计池

组织方式:**记账 + 自动汇总**。

- **记录只追加不改写**:每条写「做了什么决定 / 为什么 / 关联需求 / 作废哪条」;旧条标作废不删。便宜,门禁好查「这需求留没留记录」。
- **汇总文档是生成物**:工具从有效记录确定性生成每模块「当前设计」,幂等、不手改;人与助手平时读汇总,历史与理由查记录。记录是账本,汇总是余额。
- **风格定稿单列、带版本**;升版可选产出「离风格资产报告」。
- **美术主动产出**(概念、风格定稿)走设计池入库,不走需求池——需求池进「要做什么」,设计池进「定成什么样」。

冲突处理:入库或影响评估发现新需求与已有设计/需求矛盾时,经助手/卡片给**策划三选一**:

| 选择 | 语义 | 系统动作 |
|---|---|---|
| 改新的 | 让步于既有设计 | 助手辅助改写新需求,重新入库 |
| 改旧的 | 新方向胜出 | 新需求自动挂「设计变更」义务:完成时作废/替换旧设计记录;旧需求打「已被 REQ-xxx 演进」标 |
| 强制推送 | 先干了再说 | 新需求照常入库执行;新旧**配对**进 `冲突列表.json` 挂账 |

强制推送的债务约束:冲突**不拦执行**,但验收报告必列未决冲突、设计汇总文档把冲突区域标红、助手据冲突列表提醒后续涉区需求;每条冲突必须有人裁决销账(裁决 = 事后补选「改新的/改旧的」)。

## 四、同步与供给

### 同步(把内容收回来)

- **字段所有权,不做合并**:内容字段归策划端(状态到「已确认」后锁定);状态字段归工程,下游只读。同步只朝所有权方向单向复制,冲突从结构上消灭。
- 入站:下游 → `Inbox/` → `pool.pull`(合并 schema 校验、分类型必填)→ 入池自动 commit(`[入库] REQ-0042 签到系统`)。拒收把字段级错误(用生成的错误文案)回贴 bitable 评论/卡片,策划原地改。
- 出站:任务 PR 合并触发 `pool.push`:回写状态 + 发摘要卡片(带截图/录屏)。
- **已确认后的变更 = 打断重规划**:变更到达 → 任务暂停 → diff 新旧需求快照生成 `05-变更影响.md` → 沿工作项依赖图**标脏**受影响项 → 回方案/评估关(原有人审则再人审)→ 脏项重跑、净项保留。最终交付永远对齐最新需求,不留中间态残留;重规划计入任务预算,超了停下问人。

### 供给(把编辑器铺出去)

`需求.schema.json`(基线⊕项目合并后)经 `bridge.provision --driver feishu` 生成四样:

1. **bitable 建表描述**:枚举→单选、必填→必填,表结构即第一道校验。分类型必填 bitable 原生做不了,用「按类型三张表单写同一张表」+ 校验器兜底。
2. **助手配置包**:schema + 填写指南 + 正反例(历史真实被验收/被打回的需求)+ 设计池汇总摘要 + 术语表 + 当前模块清单。助手价值排序:**设计一致性把关 > 格式合规**——策划提需求时它能当场指出与既有设计的冲突并发起三选一。
3. **校验错误文案**:拒收回贴用,和校验器同源生成,不会两张皮。
4. **专项表**:一行一专项、每职责一个人员多选「认领」列;认领改动走既有同步通道拉回,零新接口。

助手两形态 = 同一 port 的两个 driver:

| | A. 平台内置(Aily 配置包) | B. 自托管(lark-event 订消息) |
|---|---|---|
| 知识 | 配置包快照,provision 时刷新 | 直连仓库,现查设计池、现跑校验器 |
| 成本 | 零运维,人工导入一次 | 常驻进程 |
| 排期 | v1 | v2 |

防漂移门禁:配置包存生成时 `schema hash + 设计池 hash`,与当前值对账,不一致红。
schema 带版本号;升版时 provision 产迁移说明,存量需求记录打版本标。

## 五、执行引擎与人工干预

任务 = 任务目录 + git 分支:

```
_Tasks/REQ-0042/
  00-需求.json         ← 池子快照(变更后追加 00-需求.v2.json)
  05-变更影响.md       ← 仅发生变更时
  变更/                ← 已确认后的下游改动(字段级累积 diff)
  10-方案.md           ← 拆解 + 设计记录草案        [关卡:可配人审]
  20-工作项/           ← 一项一文件(域/依赖/状态)
  30-产物/             ← 资产 + 溯源边车;代码落在分支上
  50-验收报告.md       ← 门禁输出 + 截图 + 未决冲突
```

- **可续跑**:`task.run REQ-0042 --from 30`;人改任意中间文件(哈希检测)即视为权威,从该阶段续跑。
- **干预三档**:全自动 / 关卡审(方案、选片、合并等配置点停)/ 接管(人直接改文件、上分支提交)。
- **PR 终审默认人审**;程序可按放行策略对低风险业务代码开自动放行(高危路径基线锁死,细则子文档 03 §九);合并触发回同步。
- **选片**:资产工作项产 N 个变体拼 contact sheet,飞书交互卡片发出,点选即过卡,手机上就能审。
- **门禁分工**:机器查规格(命名/尺寸/POT/面数/图集归属/导入设置/溯源边车),人查审美。

### 阶段细则(一条需求的完整旅程)

> 步骤中出现的 bitable/飞书卡片/ComfyUI/Blender 均为**当前 driver 的示名**——阶段逻辑只依赖 port(§七),换 driver 步骤不变。

**阶段 0 · 提出与入库**(常开,无人值守)
1. 策划在 bitable 填单,或与助手对话由它产出合规草稿写回表。
2. 同步器发现新/改记录(唤醒:事件推;轮询:定时扫),拉到 `Pools/Inbox/`。
3. `pool.pull` 校验:骨架字段、分类型必填、枚举合法。
4. 不过 → 字段级错误回贴 bitable 评论,记录留在 Inbox,策划改完自动重走。
5. 过 → 冲突扫描(对设计池汇总 + 存量需求);有冲突 → 三选一卡片(§三),按选择处理。
6. 入池 `REQ-xxxx.json`,状态=草稿,自动 commit `[入库] REQ-xxxx 标题`,状态回写 bitable。
人工点:仅冲突三选一。

**阶段 1 · 确认(扳机)**
1. 白名单确认人拨状态到「已确认」;非白名单的状态改动被同步器拒绝并还原。
2. 内容字段锁定:此后策划端改动不直写池子,走变更通道(横切 A)。
3. 引擎按模式接活:唤醒/轮询自动入队;值守等人在面板点「跑这条」。

**阶段 2 · 方案**
1. 建 `_Tasks/REQ-xxxx/` + 分支 `task/REQ-xxxx`,快照 `00-需求.json`。
2. AI 读需求 + 设计池汇总 + 相关代码与规范,按类型产出:
   - 系统:玩法拆解、模块归属、设计记录草案、工作项清单(域 + 依赖图)、验收核对表;
   - 修改:影响评估(动哪些文件/资产/配置、波及面),工作项 ≤ 阈值走快道(可配免审),超了升完整方案;
   - 缺陷:复现分析、失败测试计划、疑似根因,工作项通常一两个。
3. 写 `10-方案.md` + `20-工作项/*.json`;方案格式门禁(依赖无环、每项带验收点)。
4. 关卡:方案人审(系统类型默认人审);通过/打回,打回带意见 AI 改案重提。

**阶段 3 · 工作项执行**
按依赖图拓扑序(v1 串行),每项状态实时落文件(面板 DAG 变色):
- 代码项:改代码 → 每改跑秒级 dotnet test → 批量后十秒级 → 涉 Unity 侧必跑分钟级 gate-unity → 绿即完成;
- 配置项:改 Luban 源 → 生成 → 镜像哈希对账;
- 资产.生图项:`art.generate`(配方 ⊕ 锚点)→ 机检预筛 → contact sheet → 选片卡片[必人审] → 换一批(反馈词重跑)/接管(人产物放回)→ `art.import`(落点 + 导入设置)→ 资产规格门禁;
- 资产.模型项:生成粗模 → 三视图选片[必人审] → Blender 加工(减面/UV/pivot/命名)→ 导入 → 规格门禁;
- 文档项:模块文档更新、设计记录定稿准备。
失败:门禁红自动修复 ≤N 次,仍红停下标红、卡片喊人;driver 挂了只挂起该域工作项,其余继续。

**阶段 4 · 集成验收**
1. 全项完成 → 全量门禁(模板四级 + §十新增)。
2. 按验收核对表逐条核:能自动化的落成测试,不能的实机截图/录屏留证。
3. 履行设计池义务:系统 → 设计记录正式入库并重生成汇总;修改动了设计 → 变更记录;「改旧的」义务在此作废旧记录。
4. 写 `50-验收报告.md`:门禁结果 + 核对表 + 截图 + 未决冲突 + 成本消耗。

**阶段 5 · 双线终审**
- 策划线:状态→待验收,摘要卡片(截图/录屏)发策划,审「是不是我要的」;不对 → 意见按变更走横切 A。
- 技术线:AI 对抗预审先行(阻断级发现不发 PR、直接回修)→ 发 PR(附审查包:变更地图/方案对照/预审报告/验收报告/按工作项分 commit)→ 程序按风险分级审(低风险业务命中放行策略可自动放行,其余人审);打回 → 意见落文件,AI 逐条修并产回应清单,3 轮未过建议转接管;打回意见入意见库喂晋升与预审。细则见子文档 03 §九。
- 两线都过 → 合并:人点,或命中程序配置的自动放行策略(仅低风险业务,高危路径永不自动;放行入流水可抽查可回滚)。

**阶段 6 · 回同步与归档**
1. 合并触发 `pool.push`:状态→已完成回写 bitable,完成卡片(带截图)发群。
2. 本需求涉及的冲突销账、冲突列表更新。
3. 任务目录归档留存(复盘用);成本入账面板。

**横切 A · 打断重规划**(已确认后的变更,任意阶段可发生)
1. 变更被同步器拦下(不直写池子),生成变更记录;任务暂停——当前原子步骤跑完即停,横幅「重规划中」。
2. diff 新旧快照 → `05-变更影响.md`,沿依赖图标脏;`00-需求.v2.json` 成新基准。
3. 回阶段 2 方案关(原配人审则再审)→ 脏项重跑、净项保留。
4. 停在待验收/PR 时变更:旧卡片与 PR 标作废,重走后重推。

**横切 B · 预算熔断**
每任务带 token/生图调用预算,重规划同池计数;超限即停问人:追加、砍范围、或放弃。

### 任务视图(流水线图)

模板 Dashboard 现有的是**构建流水线**视图(`Pipelines/流水线定义.json` 四条流水线,PipelineRunner 跑步骤、LogEventChannel 流日志)——工具链级,不是任务级。创作管线在同一 Dashboard 加「任务」页:

- **两级结构,同一页面**:列表级看全局——每任务一行(标题/专项/阶段/进度条/**当前等谁**/等待时长),可按专项、状态、「等我的」筛选(等我的置顶);点行进详情级。
- 详情级两层图:上为**阶段轴**(00 需求 → 10 方案 → 20 工作项 → 30 产物 → 50 验收),下为**工作项依赖 DAG**;节点着色:完成 / 执行中 / 待审(停在关卡) / 标脏 / 排队。顶部带提出人、各职责认领人、预算条与**责任视图**(当前关卡推给谁、等多久、历史裁决)。
- **渲染器零状态**:纯读 `_Tasks/` + 工作项文件 + git,不另设进度数据库——铁律 2 的第二次回报,视图不可能与真实状态两张皮,人手改了中间文件刷新即所见。
- 关卡操作就在图上:停等节点高亮,「通过/打回」按钮即此;同时飞书卡片推送(带回链)。
- 实时日志复用 LogEventChannel,跟随当前执行中的工作项。
- CLI 同源出简版:`task.status REQ-0042` 文本树,无面板也能看。

**打断的可见性**(打断是显式事件,不是悄悄换状态):

1. 变更到达 → 任务横幅进「重规划中」,图冻结;
2. 重规划完成 → 标脏节点变红待重跑、保住的绿色不动,`05-变更影响.md` 挂在横幅上——一眼看清「哪些保住了、哪些重做」;
3. 若打断时有人正停在关卡审,旧卡片作废,重规划后重新推送。

### 引擎模式(Dashboard 加「引擎」页)

| 档 | 触发 | 依赖 |
|---|---|---|
| 唤醒 | 飞书事件流推送即醒 | 开放平台事件订阅 |
| 轮询 | 定时扫池子「已确认」 | 无——事件权限开不了的兜底档 |
| 值守 | 永不自动,人点一条跑一条 | 无 |

- **入库通道独立于三档,常开无人值守**:只写数据文件、不执行任何代码,风险面与执行完全不同。
- 确认人白名单也在「引擎」页管理。
- v1 并发策略:单任务串行、排队;并行(worktree 隔离)留 v2。

### 职责路由与单人模式

角色(策划/美术/程序)在系统里只是**卡片路由配置**,机制四件套:

- **成员表** `Pools/组织/成员.json`(管理员编辑):每人 = 联系方式(飞书 open_id)+ **默认职责**集合 + 是否确认人。默认职责只在路由第③步(未认领时推给谁)起作用。
- **路由表** `Pools/组织/卡片路由.json`(数据可改):卡片类型 → 职责。默认:选片→美术;待验收→该需求的提出人(不在成员表则落任意策划);方案审/终审 PR→程序;冲突三选一→策划;熔断/失败停机/预算→管理员。
- **专项**(范围层,制定归策划):`Pools/专项/EP-xxxx.json`——策划建专项(如「水下遗迹场景包」)、往下挂需求(骨架 `专项` 字段,可空)。成员**认领**专项,且**认领不限默认职责**(程序可临时认领某专项的美术);认领是专项表的一个字段,v1 由飞书 bitable 专项表直接编辑、经既有同步通道对齐(**零新接口**),Web 面板认领按钮留后期。专项还带「默认锚点」与进度汇总;引擎执行不感知专项,纯路由+规划层。
- **路由四步**:① 卡片类型→职责;② 需求所属专项该职责有认领人→只推认领人(组内先到先得;显式认领可跨默认职责);③ 未认领/无专项→按**默认职责**全员先到先得,**首次处理即隐式认领**(隐式仅限默认职责内,跨职责必须显式);④ 职责无人→管理员兜底。身兼多职收并集。

单人模式即兜底规则的退化情形——不是单独一套逻辑。生图/模型生成本就由引擎在阶段 3 自动调用,人只存在于关卡;每个关卡都是旋钮(自动/人审),单人模式按需下调:

- 选片可配 **AI 自选**:机检过滤后按「与风格定稿的距离」打分取最优;contact sheet 与全部溯源留档,人随时翻案重选,重选=变更自动重跑下游。
- AI 可**主动提案需求**:从方向文档缺口/设计池遗留/验收报告尾巴生成完整策划案(过同一套校验),入池**状态=草稿**;也可由人一句话展开成全案。
- **闸门设计**(非能力限制):① 确认扳机永不自动——AI 不得自确认,否则自己给自己派活;② 熔断后追加预算永不自动;③ 合并**默认人审**,程序可按放行策略对低风险业务显式开自动放行(高危路径基线锁死、放行入流水可抽查可回滚)。「要不要做、花不花钱」焊死在人手里;「能不能进」默认在人手里、松绑权归程序且有底线。

极限日常 = 早上批提案(点已确认)、白天全自动(冲突与熔断才找人)、晚上验效果+合并。

## 六、统一面板(本地 Web)

创作管线的全部可视化收进**一个本地 Web 面板**——扩展现有 `Tools/Dashboard`(DashboardServer 同栈续建),不新起工具。两条原则:

1. **面板零私有状态**:一律渲染文件系统与 git 的现状,不设自己的数据库;关掉面板,事实源无损。
2. **按钮皆命令**:每个写操作背后都是一条 CLI 命令(`task.approve`、`conflict.resolve`、`bridge.provision`……),面板只是命令层的皮——没有面板时终端能做完全等价的事,权限与审计和命令层同一套。

与飞书的分工:**飞书卡片管「需要人立刻决定的事」的推送**(选片、关卡、冲突三选一),**面板管全景与追溯**;卡片带面板回链。

## 七、可插拔分层

| 层 | 放什么 | 例 |
|---|---|---|
| Skill | 流程 + 判断 | 资产 brief 怎么写、审什么、同步手顺 |
| CLI 命令 | 确定性操作,可测试、可进门禁 | `pool.pull`、`art.generate --driver comfyui` |
| MCP | 有状态的活工具会话 | blender、comfyui、unity-editor |

- **可插拔切在 CLI driver 层**:稳定契约 = 资产请求 JSON 进、产物 + 溯源边车出;`Config/下游.json` 一行换 driver,上层 skill 与工作流零改动。MCP 是 driver 的实现细节,不是抽换点。
- **配置两层拆分**:`Config/下游.json` 进 git 团队共享(域→driver 映射、端点、默认参数);`Config/本机.json` gitignore(密钥、GPU 地址、本机路径)。**密钥永不入库**,共享配置只存密钥名;面板「下游」页是这两个文件的编辑器,新项目首开时整列红点、逐项填绿即开工,兼当环境安装清单。
- **密钥与账号归属:配置跟机器走,不跟成员走**。AI 调用全由引擎发起,成员只点卡片——零密钥零安装;密钥只住执行机(v1 一台,即项目的「AI 钱包」)。成员想自己跑任务 = 把自己机器变执行机,用项目 key 或自带 key;消耗记录带执行机标识,混用可对账。接管产物只认文件不认账号——个人 AI 工具与账号天然在系统边界外。
- **风格锚点是仓库资产**:参考图、色板、LoRA、ComfyUI workflow JSON 全部入库版本化,不留在工具侧。换后端的最大真实风险是风格漂移,锚点在仓库才有重校准基准。

### Port 清单(下游的正式接口)

| Port | 职责 | v1 driver | 候补 |
|---|---|---|---|
| 需求编辑端 | 表单、状态展示、拒收回贴 | 飞书 bitable | 腾讯文档、纯 Web 表单 |
| 消息卡片 | 选片/关卡/冲突/完成的推送与回调 | 飞书 IM 卡片 | 企微、面板内通知 |
| 助手 | 提需求陪聊、冲突三选一发起 | Aily 配置包 | 自托管 agent(lark-event) |
| 生图 | 资产请求 → 图变体 + 边车 | ComfyUI | 云 API(即梦/万相) |
| 模型生成 | 资产请求 → 粗模 | Tripo/Meshy/混元3D | — |
| 模型加工 | 粗模 → 合规资产 | Blender MCP | — |
| 动画 | 资产请求 → 动画资产 | (port 已定,实现延后) | 动作库+重定向、生成式 |
| 执行后端 | 跑方案/代码/评审的 LLM | Claude | 任意可换 |

保证「随时可换」的四个机制:

1. **driver 自述**:每个 driver 夹一份 `driver.json`——实现哪个 port、支持的契约版本、配置字段 schema、试跑命令。面板「下游」页按自述**动态渲染**配置表单,加 driver 不改面板。
2. **接入成本恒定**:新下游 = `Bridges/<名字>/` 一夹(port 命令实现 + 自述)+ `Config/下游.json` 一行;引擎、skill、面板零改动。
3. **下游边界门禁**(§十):引擎与管线层代码禁止出现具体 driver 的符号/字符串,只准经 port 调用——与模板「可选功能引用范围」门禁同款,机器把关不靠自觉。
4. **契约版本化**:port 契约(资产请求/溯源边车/同步记录)带版本号;driver 自述声明支持版本,不匹配在试跑即红;契约升级时老 driver 显式适配。

换下游不搬数据的底气:**内容从不住在下游**——池子、锚点、配方、溯源全在仓库;换需求编辑端只是换一层皮,历史零迁移。

### 运行形态:线上平台与本地终端

「线上/本地」不是新的 port,是 **driver 自述里的一个属性**(`形态: 线上|本地`)。对引擎一切 driver 都是「端点 + 契约」,调用同构;差异收敛在三轴:

| 差异轴 | 线上平台 | 本地终端 |
|---|---|---|
| 能力来源 | 平台功能,配置在线上(key/模型选择),任何机器可用 | 本机安装的 skill/插件/节点/模型,绑定具体机器 |
| 成本模型 | 按次计费 → 预算硬护栏 + 限流 | 硬件占用 → 并发=1 排队,费时间 |
| 可复现性 | 平台会悄悄升级模型 → 溯源记「平台+模型版本+日期」 | 环境靠依赖清单重建 → 换机器可对账 |

本地形态的**能力对账**机制:

1. 本地 driver 必须实现「能力探测」:枚举本机已装 skill/节点/模型。
2. 配方/请求声明依赖(`依赖: [节点X@版本, 模型Y, LoRA Z]`);试跑时对账**依赖 ⊆ 本机能力**,缺项列清单 + 安装指引——协作者 clone 后面板直接告知差什么。
3. 能力清单文件化进仓库(名称+版本+来源);大文件(模型 checkpoint)刻意不进,学 HybridCLR:现装 + 装完打报告。

两种理解都被覆盖:美术工具(线上生图 API vs 本地 ComfyUI)如此,美术执行端(线上 agent 平台 vs 装满 skill 的本地终端)亦然——port 契约不变,形态只是自述字段。同一配方可有线上/本地两个实现变体(prompt 模板 vs workflow JSON),共享同一套风格锚点。

## 八、美术四域

| 域 | v1 | 备选/后续 |
|---|---|---|
| 生图 | ComfyUI driver:workflow JSON 按资产类型做「配方」(图标一套、立绘一套),入库版本化 | 云 API driver(即梦/万相等)兜底 |

资产存放:

- **当选定稿必须进项目仓库 git**——游戏引用它、协作者靠它跑,没有商量余地。模板仓库零资产。
- **落选变体不入库**:留 gitignore 缓存目录 + 全量溯源记录(模型/prompt/seed/配方版本/定稿版本),算力换仓库体积,随时可重生成。
- git LFS 为项目层可选项,测试项目先不用。
- 一切产物带溯源边车,资产规格门禁查其存在。

## 九、规范分层(引擎/数据分离)

```
规范/
  基线/          ← 模板级,全仓生效;项目零手改(hash 门禁),template.upgrade 整包替换
  项目/          ← 项目级,全仓生效;项目自由改
  业务/<模块>/   ← 业务级,只对该模块的代码目录与资产落点生效(位置即范围)
生效规范 = 基线 ⊕ 项目 ⊕ 业务(就近生效;收紧任意,放宽需上层声明可覆盖)
```

- **检查器引擎写死**随模板走;数值、名单、矩阵全是数据。命名检查引擎通用,前缀表是项目的;预算对账引擎通用,预算数值是项目的。
- **新基线规则带存量违规落地 → 棘轮基线**:记录当前违规数为基线,只拦新增,存量进迁移账本慢慢烧。
- **需求 schema:骨架写死、字段开放**。工作流机器只编码在骨架字段上;门禁查项目 schema 是基线的合法扩展(骨架字段全在、状态机枚举无破坏性变更、扩展字段不与骨架重名)。
- **设计规范:格式模板化、内容项目化**。模板规定风格定稿必须有色板/负面清单/版本,游戏长什么样全是项目层的事。
- **规则来源双向**:自下而上 = 晋升流程(评审/返工同类问题 N 次 → AI 提议 → 人批准入层);自上而下 = 管理员在面板人述规则 → `spec-author` skill 生成规则数据与检查器(带配套测试)→ **在现仓库试跑出命中预览** → 管理员确认入层,存量入棘轮基线。两路产物同构,都落 spec-author 判定的层级目录(项目级/业务级),provision 刷到助手。
- **提交时检查**:仓库钩子(`spec.hooks-install` 一条命令装)对暂存文件跑秒级增量子集(命名/资产规格/池子校验/基线未手改);慢检查留 gate 与 CI,钩子与 gate 同一套检查器。
- **规则执行三档**:代码检查器优先(确定性、毫秒级,进钩子与 gate)→ 代码表达不了的转 **AI 判定项**(规则自带判定提示词,方案/验收阶段批量跑、按文件 hash 缓存;结果为软警告,默认不拦、可按规则配置拦)→ 再不行才是人审项(落 `规范/方向/` 与设计池定稿,助手提醒、选片/终审执行)。spec-author 按此顺位生成;AI 判定项成熟后可提案**下沉**为代码检查器,判定成本随时间趋零。
- **增加不分级,查看分级**:提规则的人只输入描述 + 可选业务归属,层级由 spec-author 自动判定并在命中预览显示落位;面板浏览按 项目级/业务级(按模块)/基线/方向 分页。
- **`project.create` 约束**:`规范/基线` 与检查器引擎同 `com.hsgframe.*` 一样**不参与改名替换**,否则文件被重命名过,`template.upgrade` 做不到整包零冲突替换。

## 十、新增门禁清单

| 门禁 | 查什么 |
|---|---|
| 池子校验 | 入池文件过合并 schema;分类型必填齐全 |
| 扩展合法性 | 项目 schema 是基线的合法扩展 |
| 设计义务 | 系统需求完成必有关联设计记录;修改动了既定设计必有变更记录 |
| 汇总幂等 | 设计汇总文档 = 记录的确定性生成物,重跑无 diff |
| 供给对账 | 助手配置包/建表描述的 hash 与当前 schema + 设计池一致 |
| 基线未手改 | `规范/基线` 文件 hash 对账 |
| 资产规格 | 命名/尺寸/POT/面数/图集归属/导入设置/溯源边车存在 |
| 冲突可见 | 验收报告列全未决冲突;冲突列表条目带裁决人字段 |
| 下游边界 | 引擎与管线层不得引用具体 driver 符号/字符串,只准经 port 接口 |
| 层边界 | 协作/过程/生成数据不进 `UnityProject/Assets`;游戏代码不引用 `Pools/` `_Tasks/` |
| 生效规范幂等 | `_Generated/生效规范/` 重合并无 diff |

## 十一、安全与成本

- **需求文本按不可信输入对待**——它会流进一个有 shell 与仓库写权限的 agent:
  - 「已确认」扳机只归白名单确认人;
  - PR 终审默认人审;自动放行仅限程序显式配置的低风险业务范围(高危路径与骨架变更基线锁死、不可覆盖),放行全量入流水可抽查可回滚;
  - 执行环境按最小权限跑。
- **成本护栏**:per-task 的 token/生图调用上限,超了停下问人;打断重规划计入同一预算。
- **验收报告必须带截图/录屏**——门禁绿证明「没坏」,证明不了「是策划要的」。
