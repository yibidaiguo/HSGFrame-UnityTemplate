# 规范与门禁(创作管线子文档 07)

> 上游:总方案 §九/§十。含管理员界面的规则生成流与提交钩子。

## 一、目录

```
Specifications/
  基线/(模板级,全仓生效;模板发,hash 锁,project.create 不改名)
    需求骨架.schema.json | 管线模板.基线.json | 命名规则.json | asset-spec.baseline.json | 检查器清单.json | 改名豁免清单.json
  项目/(项目级,全仓生效;项目自由改)
    requirement.extension.json | 命名前缀表.json | asset-spec.json | 依赖矩阵.json | 域.json | 棘轮基线.json | release-policy.json
  业务/(业务级,只对该业务生效)
    钓鱼/ | 签到/ | …(文件与项目级同构:asset-spec.json、release-policy.json 等,键就近覆盖)
  Proposals/
    P-0003-图标禁背景板.json     ← {规则描述, 依据, 生成的检查器/数据, 命中预览, 状态: 待批/已入层/已拒}
  方向/
    项目方向.md | 框架原则.md    ← 「定成什么样」的顶层文本,进 provision,方案阶段必读
```

**位置即范围**:规则住哪一层就管多大——基线/项目全仓生效;`业务/<模块>/` 只对该模块的代码目录与资产落点生效(默认范围取模块注册表,规则可带「范围补充」收窄)。业务目录名必须对应已注册模块,门禁查,防拼错。

美术规范按 §三 三档落位:代码档进资产规格数据 + 检查器;AI 判定项随规则文件带判定提示词;纯审美进 `方向/` 与设计池定稿。

## 二、合并语义(基线 ⊕ 项目 ⊕ 业务)

- 三层就近生效:业务级在自己范围内覆盖项目级,项目级覆盖基线——**收紧任意,放宽仅限上层标了「可覆盖」的键**。
- 数组默认追加;骨架必填、状态机枚举、检查器清单不可覆盖。
- 合并器按范围输出 `_Generated/EffectiveSpecifications/`(全局一份 + 每业务一份);「生效规范幂等」门禁重跑无 diff。

## 三、规则执行三档

| 档 | 判定者 | 时机 | 结果 |
|---|---|---|---|
| 代码检查器 | 确定性代码 | 提交钩子(增量)+ gate(全量) | **硬红**,拦 |
| AI 判定项 | 执行后端按规则自带的「判定提示词」 | 方案审前 / 验收阶段批量跑;按文件 hash 缓存,未改不重判;**不进钩子** | **软黄**,进验收报告,默认不拦、可按规则配置拦 |
| 人审项 | 人(关卡卡片) | 选片 / 方案 / 终审 | 关卡裁决 |

- `spec-author` 按「代码 → AI 判定 → 人审」顺位生成,能落哪档落哪档。
- **下沉通道**:AI 判定项运行成熟(误报可控、规则可形式化)→ 自动提案转代码检查器,走晋升同款流程;判定成本随时间趋零。

## 三·一、新增检查器清单(实现要点)

| 检查器 | 输入 | 判定 |
|---|---|---|
| 池子校验 | Pools/Requirements/* | 过合并 schema、文件名=id、分类型必填 |
| 扩展合法性 | 项目 schema | 骨架完整、无重名、枚举无破坏性变更 |
| 设计义务 | 已完成需求 × 设计记录 | 系统类型关联非空;「改旧的」义务闭合 |
| 汇总幂等 | Designs | 重生成无 diff |
| 供给对账 | fingerprint.json | schema hash + 设计池 hash 一致 |
| 基线未手改 | Specifications/Baseline | hash 清单一致 |
| 资产规格 | 落点资产 × asset-spec.json | 逐项 + 边车存在且合法 |
| 冲突可见 | 冲突列表 + 验收报告 | 未决冲突全列出、条目字段齐 |
| 下游边界 | 引擎/管线代码 | 无 driver 名符号/字符串 |
| 层边界 | 仓库路径 + 产品层代码 | 协作/过程/生成数据不在 `UnityProject/Assets` 下;游戏代码不引用 `Pools/` `_Tasks/` |
| 生效规范幂等 | _Generated/EffectiveSpecifications | 重合并无 diff |

全部挂进模板既有 `gate.ps1` 框架(追加清单条目);单跑入口 `gate.ps1 -Only 资产规格`。

## 四、提交钩子(每次提交都检查)

- 安装:`spec.hooks-install`(设 core.hooksPath 指向仓库内钩子目录,clone 后一条命令)。
- pre-commit 只跑**秒级增量子集**:对暂存文件做命名 / 资产规格 / 池子校验 / 基线未手改——快到无感,不劝退提交。
- 慢检查(汇总幂等 / 供给对账 / 下游边界)留给 gate 与 CI;钩子与 gate 用同一套检查器,只是范围不同。
- 不跳钩子(模板既有纪律);钩子红 = 当场改。

## 五、棘轮基线

`Specifications/Project/棘轮基线.json`:检查器 → 允许存量数。新跑违规数 > 基线 → 红;< 基线 → 提示可收紧。收紧走单独提交,信息带 `[基线收紧]` 标记(同「测试变更」仪式)。

## 六、规则来源之一:晋升(自下而上)

返工/评审里同类问题第 N 次(执行后端在验收阶段统计)→ 生成提案进 `Proposals/` → 面板规范页待批 → 人批准 `spec.promote`:数据入判定层级(项目级/业务级)、按 §三 顺位落执行档;拒绝 → 已拒(不再重复提议同款)。

## 七、规则来源之二:人述生成(自上而下,管理员界面)

流程(面板规范页「新增规则」→ `spec-author` skill):

1. 输入只有两项:人话描述 + **可选业务归属**。**没有「选级别」控件**——提规则的人不关心层级。
2. skill 自动判两件事:
   - **判级**:内容只涉某业务 → 业务级(落 `Specifications/Business/<模块>/`);通用 → 项目级。给了业务归属则直接业务级。
   - **判执行档**(§三顺位):现有引擎参数能表达 → 只产规则数据;需新逻辑 → 生成检查器脚本 + 配套测试(进 Solutions 测试工程);代码表达不了 → 生成 AI 判定提示词,标「AI 判定项」;纯审美 → 转方向条目,标「人审项」。
3. **命中预览**:现仓库试跑,报「N 处命中」+ 明细 + **落位提示**(「将作为业务级规范落在 Specifications/Business/钓鱼/」)——影响面和落位一起看,判错当场改。
4. 确认入层:数据/检查器落**判定的层级目录**,存量违规入棘轮基线,一次 commit `[规范] 新增规则 xxx`。
5. 供给对账变红 → 重跑 provision,助手同步新规则。

两路(晋升 / 人述)产物同构,都落判定的层级目录,面板同一处管理。

## 八、template.upgrade 与改名豁免

- 升级:拉新模板 → 整包替换 `基线/` + 检查器引擎 + 管线引擎 → 协作数据结构有变时执行存量迁移(池子文件批量升版,迁移脚本随模板发)→ 跑全门禁 → 新增违规入棘轮与迁移账本。**协作数据的结构与机器跟随框架,内容跟随项目;产品数据完全归项目**。
- `project.create` 改名豁免清单(不参与命名空间替换):`com.hsgframe.*`、`Specifications/Baseline`、检查器引擎、创作管线引擎与 Bridges 框架层。豁免清单本身在基线里,门禁核对。
