## 一、结论先写：**没验证成，而且这一轮验证不了**

**不要把这份文档读成「已验证不可行」，也不要读成「已验证可行」。它的结论是「未验证」。**

三条卡死的原因，每条都是硬的：

1. **锁定决策 6 写死了「飞书 API 不在可验范围」。** 这不是本轮偷懒，是 P1 立项时就定的边界——
   driver 只落契约与离线产物，真调用留桩。要改这条得重新走设计审查。
2. **没有凭据，也不该有。** 程序化导入要飞书应用的 app secret 与 Aily 的 agent 管理权限。
   锁定决策 5 是「密钥永不入库」，执行这台机器上的 `Tools/CreationPipeline/Config/local.json` 至今是空的。
3. **没有租户。** 就算有代码有凭据，也需要一个真实的飞书租户 + 一个开了 Aily 的应用来打。
   模板仓库里不存在这样的东西，也不该存在。

所以本批**没有**去写任何调用 Aily 的代码。写了也只能是一段谁都没跑过的桩，
它会以「已接入」的样子躺在仓库里骗下一个接手的人——那比不写坏得多。

## 二、这一批实际交付的是什么：把兜底路径做成机器能查的东西

总纲 §十三 给的兜底是「bitable 表单 + bot」，批次 3 已经把配置包本身产出来了。
本批补的是**配置包的完整性**——一个此前真实存在的洞：

> 供给对账门禁只比两个哈希。有人手工删掉 `助手配置包/知识/术语表.md`，
> 指纹照样对得上，门禁照样绿，而助手实际上少了一份知识。

落地：

- `Tools/CreationPipeline/AssistantPackageInspector.cs`：查 10 份产物在不在、是不是空文件，
  每份带一句「这份贴到哪」的人话。
- `ProvisionReconciler` 对账时顺带跑它——**产物缺一份，供给对账门禁就红**。
- 新命令 `bridge.package-check --driver <名>`：打印逐份产物状态 + 人工导入清单，
  缺件时退出码非 0。

## 三、给下一个拿得到凭据的人：go / no-go 判据

真要验这件事，按这个顺序打，任何一步失败就落到兜底：

| 步 | 要确认什么 | 失败意味着 |
|---|---|---|
| 1 | 飞书开放平台的应用能否申请到「Aily 应用管理」类权限 | 权限拿不到 → 程序化导入直接不可能，走兜底 |
| 2 | 是否存在「创建 / 更新 agent」的开放接口（而不是只有控制台 UI） | 只有 UI → 半程序化上限 = 自动生成、人工粘贴，即现状 |
| 3 | 知识库文件能否用接口批量上传并绑定到 agent | 不能 → 系统提示可程序化、知识只能手工，属半程序化 |
| 4 | 更新时能否**替换**而不是追加（否则每次 provision 都会积累重复知识） | 不能替换 → 必须先删后建，要确认删除接口存在 |
| 5 | 打一次真实往返，确认 `指纹.json` 能随 agent 一起存下来 | 存不下 → 防漂移只能靠仓库侧对账（也就是现在这样） |

**每一步的结论都要回写进这份文档，并且带上打通那天的日期与用的接口名。**
在那之前，这份文档第一节的结论一个字都不许改。

## 四、兜底路径（现在就能用，不等 spike）

1. 跑 `bridge.provision --driver feishu`，产出 10 份产物。
2. 跑 `bridge.package-check --driver feishu`，确认 10 份齐全——**这一步是新增的，
   以前没有，缺件只能靠人眼看**。
3. 照 `_Generated/Bridges/feishu/助手配置包/导入说明.md` 手工导入一次。
4. 之后每次 schema 或设计池变了，`gate.ps1` 的供给对账会变红，提醒重跑 provision + 重新导入。

第 4 步是这套兜底真正的价值：**手工导入只做一次，之后靠门禁提醒，不靠人记得。**
