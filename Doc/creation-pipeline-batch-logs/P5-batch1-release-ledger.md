## 这一批真正做的是什么

P2 批次 5 做完了放行**判定**（`ReleaseDecider` 能判自动放行还是人审），
但**放行之后什么都没有**。子文档 03「放行模式」的第四个圆点原话：

> **放行流水与抽查**：自动放行的合并全量入流水（面板审查页）；程序按比例抽查；
> 发现问题一键 revert（生成回滚 PR）+ **该范围策略自动回落人审** + 记意见库。

这一批把这一句从头到尾落上：入账 → 抽查 → 发现问题三连。

## 抽查为什么不许用随机数

「按比例抽查」最自然的写法是随机抽。**这里刻意不那么写**，两条理由：

1. **随机抽查在门禁里没法验**——同一份流水两次跑抽出不同结果，测试写不出断言。
2. **真发现问题时没法复现「当初抽的是哪几条」**。

改成**按 id 序数序均匀跨步**：`步长 = 候选数 ÷ 想抽几条`，第 k 条取下标 `(int)(k × 步长)`。
采样面照样铺得开（测试里断言了抽出来的不是相邻的前两条），而且逐条可断言。

## 回落为什么只写项目层

回落方向永远是 `自动放行 → 人审`，照决策 37 这是**收紧**，在任意层都合法——
所以 `PolicyFallbackPlanner` 不查 `可覆盖` 清单。
但它**只写 `Specifications/Project/release-policy.json`，永远不碰基线**：基线是数据推不翻的底线（决策 38），
让回落去改基线，等于把守底线的那道机制自己拆了。

而且这个类里**没有任何一处写得出 `自动放行`**——它只会往紧里改，不会往松里改。

## 执行后端这一轮报上来的三件事（都属实）

1. **`ReleasePolicyCatalogTests.cs` 不在任务书清单里，但它必须改。** 新规则是
   「基线缺 `抽查比例` 就报一条 finding」，而那个测试的基线常量原本没这个键，

   **这是我任务书写漏了**——写「缺键就报 finding」时没把既有测试的基线常量算进去。
2. **那两条 CS1570 既有警告**——见上，它验过是既有的，也说清了「0 警告」这条标准
   在基线上本来就不成立。

## 已知缺口（不阻塞，记着）

- **抽查只出「该抽哪几条」，不出「抽出来给谁看」。** 面板审查页还没有（排在 P7 批次 2）。

  真生成 PR 要起 git 与 gh，`task.spotcheck` 刻意一行 git 都不跑。
- **回落只回落「这条流水记的范围」**，不做跨条目的聚合判断
  （比如「同一范围连着三条都发现问题才回落」）。
