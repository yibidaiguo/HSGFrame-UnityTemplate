99. **一条需求从「一个文件」变成「一个目录」，路径一律经 `PoolPaths` 的访问器族。**
    `Pools/Requirements/REQ-0042/` 底下是 `requirement.json` + `index.md` + `media/` + `snapshots/`。
    迁移时把全仓 8 处 `Path.Combine(…, id + ".json")` 与 3 处枚举一并收编，
    调用方**不许再自己拼**。
    散着拼的代价不是「改起来累」——那是一次性的；真正的代价是
    **下次再加一份随需求走的东西时，没有任何办法知道还漏了谁**。
    这一次一口气加了三样（文档、媒体、快照），散着拼的话下一个人要重新翻一遍全仓，
    而且翻漏了没人会发现。
    **推论一：只搬不收等于把同一个坑挖深**，迁移与收编必须同一批做完。
    **推论二：「目录在而骨架缺」要当场报违规**，不许静默跳过——
    静默跳过的后果是一条需求凭空消失而每一道门禁都是绿的（决策 42 那一类假象）。
    落地：[A 批日志](creation-pipeline-batch-logs/REQDOC-batchA-requirement-directory.md)。

100. **规范与它的机器可读形式必须住在同一个文件里。**
    需求文档规范是一份 md：给人读的散文 + 一段 json 契约，
    `doc.render` 与 `gate.reqdoc` 只读那段 json。
    散文一份、配置一份的规范活不过三次改动——改的人只会改自己看得见的那一份，
    然后两份说的话开始不一样，而门禁执行的是没人读的那一份。
    **推论一：分层覆盖要靠形状保证，不靠校验器骂人。** 项目层那个文件只有
    「追加小节」「追加frontmatter必备键」两个键，**表达不出「删」**，
    于是「基线定的不可删」这条规矩没有绕过去的写法。
    **推论二：窄解析器要把「认不出来」降级成「读不出这个键」，不要报语法错。**
    frontmatter 只认标量 / 一层映射 / 对象列表三种形状，别的写法读不出来，
    于是「必备键缺失」替它报红——那句话人看得懂，「第 7 行缩进不对」不是。
    落地：[B 批日志](creation-pipeline-batch-logs/REQDOC-batchB-doc-spec-and-render.md)。
