# BUG 反馈簿

> **实际项目里踩到的问题写这里。** 一条 BUG 一节，编号 `BUG-0001` 顺排，只增不改号。
> 修完不删——留着是账，也是「这类问题该不该立成门禁」的证据（攒够同类就进[待办账本](Backlog.md)）。

## 怎么写一条

复制下面这段贴到「## 未处理」下面，编号取当前最大号 +1。**六项写全**，
写不全的项写「不知道」——比空着强，空着会让人以为你确认过没有。

```markdown
### BUG-00XX 一句话现象（动词开头，别写「有问题」）

- **状态**：新报
- **现象**：看到了什么。截图/日志贴路径，别贴大段原文。
- **复现步骤**：1. … 2. … 3. …（能重复出现的写步骤；偶发的写「偶发，N 次里 M 次」）
- **期望 / 实际**：本该怎样 / 实际怎样。两句话，别合成一句。
- **环境**：哪台机器、哪个项目、走的哪条路（面板 / 飞书 / 命令行 / 执行端派活）。
- **影响面**：挡不挡活。挡了写「挡」，能绕写清怎么绕的。
```

**不用你判断根因**，也不用你想修法——那是接手时的事。你只要把「看到了什么」写准。

## 状态怎么流转

| 状态 | 意思 | 谁改 |
|---|---|---|
| 新报 | 刚写下，还没人看 | 你 |
| 确认中 | 有人在复现 | 接手的人 |
| 修复中 | 复现了，正在改 | 接手的人 |
| 已修 | 改完且门禁绿；补上「修在哪个提交」 | 接手的人 |
| 不修 | 有理由不修（设计如此 / 成本不值 / 上游问题）；**理由必须写** | 接手的人 |

已修与不修的条目移到文末「## 已归档」，别删。
